# 날씨 경영 시스템 — 설계 문서

- 날짜: 2026-08-12
- 원 요구사항: 「날씨 경영 기능 개발 v0.1.pptx」 (6슬라이드)
- 상태: 설계 승인 완료 (사용자 승인 2026-08-12)

## 1. 개요

날씨 이벤트(폭우·폭설·강풍·폭염)가 임계값을 넘으면 감지하여 사업부장에게 알리고,
부서별 사전 등록 행동 지침을 템플릿 조합해 메시지 초안을 만들고,
사업부장 검토·승인 후 각 부서 담당자에게 카카오워크로 발송하는 시스템.
리조트 운영 조직(예: 곤지암리조트류) 대상. 오픈소스 파일럿으로 공개 가능해야 한다.

역할 구조는 Human-in-the-loop: System(감지·조합·발송) → 사업부장(승인·편집) → 실무자(이행).

## 2. 확정 결정 사항

| # | 항목 | 결정 |
|---|------|------|
| 1 | 프로젝트 성격 | 실서비스 — 실제 API 연동 |

| 3 | 발송 채널 | 카카오워크 봇 (무료). 어댑터로 추상화해 알림톡 등 추가 용이하게 |

| 6 | 주의보→경보 격상 | 기존 주의보 이벤트는 ESCALATED로 종료, 경보 이벤트를 새로 생성해 승인 플로우 재시작 |

| 8 | 권한 | 3역할: 시스템관리자(설정) / 사업부장(승인·발송) / 실무자(조회) |

| 10 | 인증 | **카카오워크 OAuth 전용** (로그인·회원가입 모두). 최초 로그인 시 계정 자동 생성, 역할은 관리자가 지정. 이메일 로그인 없음 (2026-08-12 사용자 결정으로 폴백 제거) |
| 11 | 초안 생성 | 템플릿 조합 (등록 지침 + 날씨 수치 삽입). AI 미사용 |
| 12 | 아키텍처 | Supabase 올인 (서버리스). NestJS 등 상시 서버 없음 |
| 13 | DB/배포 | DB·스케줄러·함수 = Supabase, 웹 = React SPA 정적 호스팅(Vercel/Netlify) |
| 14 | UI 용어 | 감지 건의 UI 표기는 **"특보"** ("이벤트" 대체, 2026-08-12 결정). 코드/테이블명은 영문 유지(weather_events 등) |
| 15 | 감지 소스 | **자체 임계값 판정 단독** — 기상청 기상특보 조회서비스 API(공공데이터포털 15000415, 시·군 단위 주의보·경보 제공)를 검토했으나 사업장 맞춤 기준 우선으로 자체 판정만 사용. API 존재는 확인됨 → 향후 공식 특보 병행 트리거로 확장 가능 |

결정 배경 메모:

- 알림톡/SMS는 오픈소스 자체 발송 불가(카카오 공식 딜러사·문자중계사 필수 유료 채널)라서
  무료인 카카오워크 봇을 선택. 카카오워크 무료 플랜의 워크봇 API 사용 가능 여부는 개발 초기 검증 항목.
- Supabase 올인은 "오픈소스 파일럿 공유" 우선순위 때문. 클론 → Supabase 연결 → 실행 흐름 확보.

## 3. 아키텍처

```
React SPA (Vite, Vercel) ── supabase-js ──► Supabase
                                            ├─ Postgres (+ RLS)
                                            ├─ pg_cron: 매시 정각 weather-tick, 매 10분 remind-tick
                                            └─ Edge Functions (Deno/TS)
                                               ├─ weather-tick  ← 기상청 공공 API
                                               ├─ remind-tick
                                               ├─ send          → 카카오워크 봇 API
                                               └─ auth-kakaowork
```

### 컴포넌트 책임

- **React SPA**: 화면 6개(로그인+대시보드+요구사항 5화면). 조회·설정 수정은 supabase-js 직접 접근(RLS 강제),
  부수효과 있는 동작(발송)만 Edge Function 호출.
- **weather-tick** (매시 정각): 기상청 초단기실황 조회 → `weather_observations` 저장 → 임계값 평가 →
  특보 생성(DETECTED→PENDING_APPROVAL) → 초안 템플릿 조합 → 사업부장 카카오워크 알림.
  활성 특보의 반복발송 조건·해제 조건·격상 조건도 매 실행 시 평가.
- **remind-tick** (매 10분): PENDING_APPROVAL 상태로 재알림 간격 경과 시 사업부장 재알림.
- **send**: 사업부장 발송 요청 처리. 메시지 스냅샷 확정 → 부서별 수신자에게 발송 → `dispatches` 기록.
- **auth-kakaowork**: OAuth 콜백 → 직원 매칭 → Supabase 세션 발급.
- **NotificationChannel 어댑터**: 카카오워크 구현체 + 콘솔/로그 구현체. 오픈소스 사용자의 채널 교체 지점.

### 날씨 파생값

- 기상청 초단기실황 제공: 시간당 강수량(RN1), 기온(T1H), 풍속(WSD), 습도(REH)
- 직접 계산: 적설 누적(신적설 관측 누적), 체감온도(기상청 공식 산식: 기온·풍속·습도 기반)

|---|---|---|
| `site_settings` | 관측 지점·전역 설정 (단일 행) | 지점명, nx, ny, 재알림 간격(분) |

| `recipients` | 수신자 매핑 | 부서별 수신 담당자, 사업부장 Alert 수신자 |

### 트랜잭션

| 테이블 | 내용 | 핵심 컬럼 |
|---|---|---|
| `weather_observations` | 매시 관측값 | 관측시각, 강수량, 적설, 기온, 체감온도, 풍속, 습도, 원본 JSON, 결측 여부 |
| `weather_events` | 감지 이벤트 | 종류, 등급, 상태, 발생시각, 종료시각, 트리거 관측 FK |
| `messages` | 초안·확정본 | 이벤트 FK, 부서별 지침 스냅샷(JSON), 상태(초안/승인됨), 수정이력 |
| `dispatches` | 발송 이력 (화면④) | 메시지 FK, 발송시각, 채널, 수신자 목록(성공/실패 포함), 반복회차 |

원칙: **`messages`는 발송 시점 스냅샷 보관** — 마스터 수정과 무관하게 "그때 보낸 내용"이 남고 원본 재발송 가능.

## 5. 이벤트 라이프사이클

상태: `DETECTED → PENDING_APPROVAL → ACTIVE → RESOLVED | ESCALATED`

- 감지: 임계값 초과 시 특보 생성 + 초안 조합 + 사업부장 알림 → PENDING_APPROVAL
- 동일 종류·등급이 이미 PENDING/ACTIVE면 신규 생성하지 않음 (중복 방지)
- 재알림: PENDING 상태로 설정 간격 경과 시 재알림 (발송은 하지 않음)
- 승인·발송: 사업부장이 편집·부서 선택 후 발송 → ACTIVE
- 반복: ACTIVE + 반복정책 충족 시 매시 자동 재발송 (승인 불필요, 승인된 스냅샷 기준)
- 해제: 해제 조건(기준 미달 / 일누적량 이하) 충족 시 RESOLVED
- 격상: 주의보 ACTIVE/PENDING 중 경보 기준 돌파 → 주의보 ESCALATED 종료 + 경보 이벤트 신규 생성
- 알림 Off인 종류는 감지 자체를 건너뜀

## 6. 화면 구성

| 화면 | 경로 | 사용자 | 핵심 동작 |
|---|---|---|---|
| 로그인 | `/login` | 전체 | 카카오워크 OAuth 단일 버튼 (최초 로그인 시 자동 가입) |
| ⓪ 대시보드 | `/` | 전체 | 현재 관측값, 활성 특보, 승인 대기 요약, 수집 heartbeat 표시 |
| ① 기준 정의 | `/criteria` | 관리자 | 4종 × 2등급 임계값, Alert 수신자. 기상청 특보 기준 프리셋 |
| ② 지침 등록 | `/guidelines` | 관리자 | 종류 탭 × 등급 × 부서 트리. 지침 2단 편집, 부서별 수신자(직원 검색) |
| ③ 초안 검토·발송 | `/events/:id` | 사업부장 | 부서 블록 인라인 수정, 부서 선택 발송(전체선택), 수신자 가감, 승인·발송 |
| ④ 발송 이력 | `/history` | 전체 | 목록 → 당시 메시지 원본 → 수정 재발송(사업부장) |
| ⑤ 알림 설정 | `/settings` | 관리자 | 종류별 On/Off, 반복정책, 관측지점, 재알림 간격, 해제 알림 토글, 수집 상태, **테스트 발송(나에게 보내기)** |
| ⑥ 직원 관리 | `/employees` | 관리자 | 직원 CRUD, 역할 지정, 카카오워크 연결 상태, **부서 미지정 신규 가입자 필터·부서 지정** |
| ⑥-1 부서 관리 (모달) | ⑥에서 열림 | 관리자 | 부서 트리 CRUD (추가/이름변경/순서/삭제). 삭제 시 소속 직원은 '미지정'으로 이동 |

카카오워크 승인 알림에는 `/events/:id` 딥링크 포함.
⑥ 직원 관리·⑥-1 부서 관리는 원 PPT에 없으나 수신자 지정·로그인 계정의 전제 조건이라 추가함 (CRUD 완결성).

### 초기 구축(0→1) 시나리오 커버리지

배포 → 최초 관리자 → 직원 가입 → 조직 세팅 → 운영 시작의 전체 수명주기를 화면이 커버한다:

1. **최초 관리자 부트스트랩**: 환경변수 `ADMIN_KAKAOWORK_ID`(카카오워크 계정 식별자)로 지정.
   auth-kakaowork가 해당 계정 첫 로그인 시 시스템관리자 역할 부여. 이후 ⑥에서 추가 승격 가능.
2. **직원 가입**: 카카오워크 로그인만으로 자동 가입 — 역할 실무자, **부서 미지정** 상태.
   부서 미지정 직원은 대시보드·이력 조회만 가능, 부서 지침은 부서 지정 후 노출.
3. **조직 세팅**: ⑥ 상단 "부서 미지정 N명" 필터로 신규 가입자를 걸러 행에서 바로 부서 지정.
   부서 구조는 ⑥-1 모달에서 관리.
4. **선행 관계와 빈 상태**: 부서 구성(⑥-1) → 부서별 지침(②) → 수신자 지정 순의 의존성이 있다.
   부서 0개 상태로 ②에 진입하면 빈 상태 화면(②-1: 안내 + 관리자에겐 '부서 관리 열기' CTA,
   그 외 역할에겐 문의 안내)을 표시한다. 같은 빈 상태 패턴을 ①(기준 미설정)·④(이력 없음)에도 적용.
5. **가동 준비 상태 가시화**: 대시보드 상단에 관리자 전용 **셋업 체크리스트 스트립**
   (관측 지점 / 특보 기준 / 부서 구성 / 부서별 지침 / Alert 수신자 — 진행률 링 + 미완료 항목 안내).
   5개 항목 완료 전에는 "시스템이 발송을 시작할 수 없습니다"를 명시, 완료되면 스트립 자동 숨김.

### 역할별 CRUD 매트릭스

| 화면/자원 | 시스템관리자 | 사업부장 | 실무자 |
|---|---|---|---|
| 특보 기준·Alert 수신자 (①) | CRUD | R | R |
| 행동 지침·부서 수신자 (②) | CRUD | R | 자기 부서만 R |
| 초안 수정·승인·발송 (③) | R | U + 발송(C) + 무시 | 자기 부서 블록 R (읽기 전용 뷰) |
| 발송 이력 (④) | R | R + 재발송/수정발송 | R (재발송 버튼 숨김) |
| 알림·지점 설정 (⑤) | RU | R | – |
| 직원·부서 (⑥) | CRUD | R | – |
| 발송 이력 삭제 | 없음 (감사 목적 보존) | 없음 | 없음 |

RLS는 위 매트릭스를 그대로 강제한다. 직원 삭제 시 수신자 매핑에서 자동 제외.

- 예외(기능적 시맨틱 컬러): 주의보 주황(#FF9500 계열)·경보 빨강(#FF3B30 계열)·성공 초록 — 재난 등급 식별용
- 폰트: Noto Sans KR (SF Pro 대체), 수치는 Inter

## 7. 에러 처리

- 기상청 장애: 재시도 2회 → 결측 기록. 연속 3회 결측 시 관리자 카카오워크 시스템 알림. 결측 시각은 평가 건너뜀(오탐 방지)
- 카카오워크 발송 실패: 수신자별 성공/실패 기록, 화면④ 실패 표시 + 부분 재발송. 전체 실패 시 사업부장 배너
- pg_cron 감시: weather-tick heartbeat 기록, 대시보드 "마지막 수집 N분 전" 표시, 2시간 지연 시 경고
- 동시성: 발송은 항상 승인된 messages 스냅샷 기준으로만 실행

## 8. 테스트 전략

- 단위 (최우선): 임계값 평가·격상·해제 판정, 체감온도 계산, 템플릿 조합 — 순수 함수 분리, Deno test
