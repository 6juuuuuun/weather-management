# 예보 기반 대시보드 설계

**작성** 2026-09-07 · **상태** 승인됨(사용자 확인 완료) · **선행** [자체 호스팅 이관](2026-08-28-self-hosted-migration-design.md)

## 1. 배경

이 시스템은 지금까지 **완전히 반응형**이다. 기상청 *초단기실황*(`getUltraSrtNcst`)으로
현재 관측만 받아, 값이 임계를 넘으면 특보를 만든다. 즉 **이미 벌어진 뒤에** 움직인다.

스키장 운영 시스템의 업계 표준(TechnoAlpin ATASSpro·SNOWMASTER)을 살펴보니 공통점이
있었다. 그쪽은 **예보로 미리 움직인다** — "제설 계획을 위해 계산된 지역 예보를 정기적으로
갱신"하고, 조건이 맞으면 공정을 준비시킨다. UI가 아니라 **관점**의 차이다.

폭설은 내린 뒤에 인력을 부르면 늦다. 이 설계는 그 간격을 메운다.

### 목적 우선순위

사용자 판정: **보고·시연 임팩트가 1순위, 단 실제 데이터로 만들어 운영에서도 쓰이게 한다.**
꾸며낸 값이나 시연 전용 화면은 만들지 않는다.

## 2. 범위

### 하는 것

- 기상청 *단기예보*(`getVilageFcst`) 수집·저장
- 일반 대시보드: 48시간 가로 스크롤 스트립 + 5일 요약
- 월보드: 48시간 스트립(비스크롤) + 5일 요약 + 지표 차트에 예보 점선
- **사전 예고 배너** — 예보상 임계 초과가 예상되면 두 화면에 표시

### 하지 않는 것

- **예보 기반 문자 발송을 하지 않는다.** 사용자 판정: 화면 표시까지만.
  발송·승인 로직(`jobs/send.ts`·`jobs/remindTick.ts`)은 한 줄도 건드리지 않는다.
- 예보로 `weather_events`를 만들지 않는다. 특보는 여전히 **실측**으로만 난다.
- 중기예보(3~10일)는 쓰지 않는다. 단기예보 5일로 충분하다.

## 3. 기술 확인 (실측)

설계 전에 실제 API를 호출해 확인했다. 추정이 아니다.

| 항목 | 확인 결과 |
|---|---|
| 인증 | **기존 `KMA_API_KEY` 그대로 동작.** 새 키·새 활용신청 불필요 |
| 서비스 | `VilageFcstInfoService_2.0` — 실황과 **같은 서비스**, 다른 오퍼레이션 |
| 기간 | **5일** (호출일 포함) |
| 간격 | **1시간** |
| 응답량 | 1회 호출에 약 900개 항목 (`numOfRows=1000`) |

받을 수 있는 카테고리: `TMP` `POP` `PTY` `SKY` `PCP` `SNO` `WSD` `REH` `TMN` `TMX`
(그 외 `UUU` `VVV` `VEC` `WAV`는 쓰지 않는다).

**이 중 `SNO`(1시간 신적설)와 `POP`(강수확률)은 지금 이 시스템이 전혀 갖고 있지 않은
정보다.** 스키장 시스템에서 눈 예보가 없다는 것은 큰 공백이다.

### 함정 1 — `PCP`·`SNO`는 숫자가 아니다

한글 문자열로 온다: `"강수없음"`, `"적설없음"`, `"1.0mm"`, `"5.0cm"`, `"1mm 미만"`.
`Number()`에 그대로 넣으면 전부 `NaN`이 되고, `NaN >= 임계`는 **조용히 false**다 —
이 프로젝트가 반복해서 고친 "값이 있는데 판정이 안 된다"와 같은 모양이다.
전용 파서를 두고, 파싱 실패는 `null`(결측)로 명시한다. `0`으로 뭉개지 않는다.

### 함정 2 — 서비스 키 이중 인코딩

공공데이터포털은 Encoding/Decoding 두 형태의 키를 발급한다. Encoding 키를 그대로
다시 인코딩하면 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 난다(실제로 겪었다).
`shared/kma.ts`의 `normalizeKmaKey()`가 이미 이것을 처리하므로 **예보 호출도 반드시
그 함수를 거친다.** 새로 만들지 않는다.

### 함정 3 — 체감온도 예보는 없다

예보에는 `feels_c`에 해당하는 값이 없다. 따라서 **폭염 예고는 기온(`TMP`)만으로
판정한다.** 실제 특보 판정은 기온·체감 둘 다 보므로, 예고와 실제가 어긋날 수 있다.
이 사실을 코드 주석과 화면 문구 모두에 남긴다.

## 4. 데이터 모델

새 마이그레이션 `db/migrations/0018_weather_forecasts.sql`.

```sql
create table weather_forecasts (
  fcst_at    timestamptz primary key,  -- 예보 대상 시각(정시)
  temp_c     numeric,
  pop_pct    integer,   -- 강수확률 0~100
  pty        integer,   -- 강수형태 0없음 1비 2비/눈 3눈 4소나기
  sky        integer,   -- 하늘 1맑음 3구름많음 4흐림
  pcp_mm     numeric,   -- 1시간 강수량. 파싱 실패는 null
  sno_cm     numeric,   -- 1시간 신적설. 파싱 실패는 null
  wsd_ms     numeric,
  reh_pct    integer,
  tmn_c      numeric,   -- 일 최저(해당 시각 행에만 온다)
  tmx_c      numeric,   -- 일 최고(   "   )
  base_at    timestamptz not null,           -- 이 예보의 발표 시각
  fetched_at timestamptz not null default now()
);
```

- `fcst_at` 기준 **upsert**. 같은 시각을 다시 예보하면 최신 발표로 덮는다.
- `fcst_at < now() - interval '1 day'`인 행은 수집할 때마다 지운다 → 상시 약 120행.
- RLS: `weather_observations`와 동일하게 로그인 사용자 `select` 허용, 쓰기는 `app_service`만.

`tmn_c`/`tmx_c`는 기상청이 하루 중 특정 시각에만 실어 준다. 일별 요약은 **이 값을 우선
쓰고, 없으면 그 날 `temp_c`의 최소·최대로 대체**한다. 대체값을 쓴 날은 그 사실을
API 응답에 표시한다(화면은 구분해 그리지 않지만, 어긋남을 조사할 때 필요하다).

일별 **대표 하늘상태**는 그 날 **09~18시(KST)** 행들의 `sky` 최빈값으로 정한다. 동률이면
더 흐린 쪽(`4` > `3` > `1`)을 쓴다. 낮 시간대로 한정하는 이유는 사람이 "그날 날씨"라고
말할 때 뜻하는 구간이 낮이기 때문이다 — 새벽까지 넣으면 맑은 날이 흐림으로 뒤집힌다.

## 5. 수집

`server/src/jobs/forecastTick.ts`를 새로 만들고 스케줄러에 등록한다.

- **단기예보 발표 시각에 맞춰 하루 8회**: KST `02·05·08·11·14·17·20·23`시 15분.
  매시 도는 것은 낭비다 — 발표되지 않은 사이에는 같은 값을 다시 받는다.
- **기동 시 따라잡기**: 마지막 수집이 3.5시간을 넘었으면 부팅 직후 한 번 수집한다.
  `weatherTick`의 `catchUpIfMissed`와 같은 처방이고, 같은 이유(컨테이너 재시작·정전)다.
- `heartbeats`에 `forecast-tick` 행을 기록한다. 기록이 없으면 멈춘 것을 아무도 모른다.
- KMA 호출 실패는 **던지지 않는다.** 마지막 예보를 지우지 않고 그대로 두며,
  `fetched_at`이 낡은 채로 남아 화면과 워치독이 그 사실을 읽는다.

## 6. 상태 표시 — `warnings` 칸을 나눈다

`/api/health/deep`의 `reasons`는 지금 **전부 "특보가 사람에게 못 간다"**는 뜻이다.
예보 수집이 멈춰도 실제 특보 발송은 정상 동작한다. 같은 칸에 넣으면 진짜 사유가 묻힌다.
반대로 아무 데도 넣지 않으면 "멈췄는데 아무도 모른다" — 이 프로젝트가 여섯 라운드
내내 고친 바로 그 결함이다.

그래서 **칸을 나눈다.**

```json
{
  "ok": false,
  "reasons":  ["SMS 발송 설정이 아직 없습니다 — 인프라 연동 대기 중"],
  "warnings": ["예보를 6시간째 받지 못했습니다 — 사전 예고가 뜨지 않습니다"]
}
```

- `reasons`가 하나라도 있으면 **503**. 지금과 완전히 같다.
- `warnings`는 **상태 코드를 바꾸지 않는다.** 기존 모니터링 설정이 그대로 동작한다.
- 6시간을 넘겨야 `warnings`에 오른다(발표 간격이 3시간이므로 2회 연속 실패 이후).
- 워치독의 6시간 점검 문자에는 `warnings`를 **싣지 않는다.** 그 문자는 "아무에게도
  못 간다"를 알리는 자리이고, 여기에 섞으면 사람이 곧 무시하기 시작한다.

`warnings`는 이 클래스(기능은 죽었지만 발송은 살아 있음)를 담는 자리로 앞으로도 쓴다.

## 7. 예고 판정

### 임계값은 특보와 같은 것 하나만 읽는다

`weather_criteria`를 그대로 읽는다. 예고 전용 임계값을 따로 두지 않는다 — 두면
배너가 말하는 기준과 실제로 특보가 나는 기준이 갈라지고, 그때 배너는 거짓말이 된다.

| 종류 | 예보에서 비교하는 값 | 임계 키 | 비고 |
|---|---|---|---|
| 폭우 | 시간당 강수량 `pcp_mm` | `rain_mm_per_hr` | 실황 `RN1`과 같은 의미 |
| 폭설 | **KST 하루 누적** `sum(sno_cm)` | `snow_cm` | 실황이 일 누적으로 판정하므로 맞춘다 |
| 강풍 | 풍속 `wsd_ms` | `wind_ms` | |
| 폭염 | 기온 `temp_c` | `temp_c` | **체감은 예보에 없다**(§3 함정 3) |

- 폭설 누적은 **KST 자정 경계**로 끊는다. UTC로 끊으면 하루가 9시간 어긋나 밤새 내린
  눈이 두 날에 쪼개진다. 이 프로젝트에서 시계 도메인 혼동은 세 번 재발했다.
- `pcp_mm`/`sno_cm`가 `null`(파싱 실패·결측)인 시각은 **판정하지 않는다.** 0으로 보지 않는다.

### 꺼둔 종류는 예고하지 않는다

`alert_settings.enabled = false`인 종류는 건너뛴다. 끈 종류의 예고가 뜨면
"껐는데 왜 뜨지"가 되고, 더 나쁘게는 "예고가 떴으니 특보도 나겠지"가 된다.

### 판정은 서버가 한다

화면은 결과만 받는다. 규칙이 화면에도 적히면 한쪽만 고쳐진다 —
`notifiable`(전화번호 판정)에서 이미 확립한 선례를 그대로 따른다.

### 어느 시각·어느 등급을 고르는가

한 종류가 여러 시각에 임계를 넘고, 주의보와 경보를 모두 넘을 수 있다. 규칙은 둘이다.

1. **종류마다 한 건만** 만든다.
2. 그 종류가 넘는 **가장 높은 등급**을 고르고, **그 등급을 처음 넘는 시각**을 쓴다.

경보를 넘는 예보에서 주의보만 말하면 대비 수준이 낮아진다. 반대로 경보 시각 대신
주의보 시각을 쓰면 실제보다 이르게 말해 신뢰를 잃는다.

### 배너

`upcoming` 중 **가장 이른 것 하나만** 말한다. 여럿이면 `외 N건`.

```
[예고]  내일 06시 폭설 주의보 예상 (신적설 7cm)
        예보 기준입니다 · 문자는 나가지 않았습니다
```

**둘째 줄은 필수다.** 없으면 "배너 떴으니 알림도 갔겠지"가 되고, 아무도 움직이지
않은 채 모두가 안심한다. 이 시스템이 다섯 번 고친 결함과 정확히 같은 모양이다.
배너의 색·라벨·위치는 실제 특보 배너와 **눈으로 구분되게** 둔다.

## 8. API

`GET /api/forecast` (로그인 필요). 두 화면이 같은 응답을 쓴다.

```ts
{
  fetched_at: string;            // 마지막 수집 시각
  base_at: string;               // 이 예보의 발표 시각
  stale: boolean;                // 서버 판정. 화면이 시간을 계산하지 않는다
  hourly: { at, temp_c, pop_pct, pty, sky, pcp_mm, sno_cm, wsd_ms }[];   // 48시간
  daily:  { date, tmn_c, tmx_c, pop_max, pcp_sum, sno_sum, sky, derived }[]; // 5일
  upcoming: { kind, grade, at, value, unit }[];                          // 예고 판정 결과
}
```

`stale`을 서버가 판정하는 이유는 `notifiable`과 같다 — 화면이 스스로 시간을 재면
두 화면의 기준이 갈라진다.

**`stale`의 기준은 §6의 `warnings` 기준과 같은 상수 하나(6시간)를 쓴다.** 두 벌로 적으면
화면은 "정상"인데 `warnings`에는 올라 있는(또는 그 반대) 상태가 생긴다.

`hourly`는 지금 시각부터 48시간, `daily`는 **오늘 포함 예보가 있는 모든 날**을 담는다.
화면은 `daily`에서 **내일부터** 그린다 — 오늘은 관측 카드와 48시간 스트립이 이미 말한다.

## 9. 화면 ① 일반 대시보드

기존 순서에 두 블록이 들어간다. 나머지는 그대로다.

```
셋업 체크리스트                     (기존, 조건부)
승인 대기 배너                      (기존, 조건부)
예고 배너                           ← NEW (조건부)
지금 — 관측 4카드                   (기존)
앞으로 48시간 — 가로 스크롤 스트립   ← NEW
5일 요약                            ← NEW
진행 중 특보 | 최근 발송             (기존)
```

### 48시간 스트립

- 1시간 간격, **가로 스크롤**. 지금 시각이 맨 왼쪽.
- 칸마다: 시각 · 하늘(`SKY`+`PTY`) · 기온 · 강수확률.
- **임계선을 함께 그린다.** 일반 날씨 앱과 이 화면이 다른 유일한 점이다 —
  "내일 35mm"가 아니라 "그건 우리 폭우 주의보 기준 20mm를 넘는다"를 같은 그림에서 말한다.
  `weather_criteria`를 읽으므로 기준을 바꾸면 선도 함께 움직인다.
- 임계를 넘는 시각은 색으로 구분한다.

### 값이 있는 줄만 그린다

비가 예보된 구간에는 시간당 강수량을, 눈이 예보된 구간에는 신적설을 보여준다.
둘 다 없으면 그 줄을 **아예 그리지 않는다**(빈 값을 `0`이나 `-`로 채우지 않는다).
겨울에는 눈이, 여름에는 비가 자동으로 앞에 온다.

### 5일 요약

날짜 · 요일 · 하늘 · 최저~최고 · 강수확률 최대 · (있으면) 일 누적 강수/적설.

## 10. 화면 ② 월보드

월보드는 **큰 화면(65인치급)에 띄우고, 3미터 밖에서 보며, 아무도 만지지 않는다.**

사용자 판정: 일반 대시보드의 정보를 **전부** 넣는다. 단 조작이 필요한 형태는 바꾼다.

| | 일반 대시보드 | 월보드 |
|---|---|---|
| 예고 배너 | O | O (특보 배너와 같은 줄, 다른 스타일) |
| 48시간 | 1시간 간격 · **가로 스크롤** | 3시간 간격 · **16칸 전부 펼침** |
| 5일 | O | O (한 줄) |
| 지표 차트 | — | **과거 실선 → 지금 → 예보 점선** |

### 자동 순환은 하지 않는다

몇 초마다 구간이 바뀌면, 지나가다 흘끗 본 사람이 **내일 오후 값을 지금 값으로 읽는다.**
이 시스템에서 가장 위험한 실패는 조용히 틀린 값을 띄우는 것이다(월보드 설계의 기존 원칙).

### 지표 차트 확장

기존 `MetricChart`는 지나온 관측만 그린다. 오른쪽으로 예보를 잇는다.

- 왼쪽 실선 = 관측 이력, 세로선 = 지금, 오른쪽 점선 = 예보 48시간
- 임계선은 이미 있다. **언제 뚫는지가 한 장에 보인다.**
- 스트립과 답하는 질문이 다르다: 스트립은 "몇 시에 어떤 날씨인가",
  차트는 "**우리 기준을** 언제 뚫는가". 후자가 벽걸이 앞에서 행동을 바꾼다.

### 카드 색과 큰 숫자는 "지금"만 말한다

**예보가 임계를 넘어도 카드를 빨갛게 만들지 않는다.** 3미터 밖에서 흘끗 본 사람이
지금 폭우가 오는 줄 안다. 예보의 초과는 점선이 임계선을 넘는 그림과 작은 표시
(`예상 초과 14시`)로만 말한다.

> 색 = 지금 · 점선 = 앞으로

### 세로 공간

월보드는 스크롤 없이 한 화면에 들어가야 한다. 세로가 부족하면 **5일 줄부터 접는다**
(가장 덜 급한 정보). 16:9 큰 화면에서는 전부 들어간다.

## 11. 오류 처리

| 상황 | 동작 |
|---|---|
| KMA 호출 실패 | 마지막 예보를 유지. `fetched_at`이 낡음 → 화면이 낡음을 표시 |
| 예보가 아예 없음(최초 설치) | 스트립·5일·예고 블록을 그리지 않는다. 빈 칸을 그리지 않는다 |
| 6시간 이상 미수집 | `/api/health/deep`의 `warnings`에 오른다(503은 아님) |
| `PCP`/`SNO` 파싱 실패 | 그 시각은 `null` → 판정에서 제외. `0`으로 뭉개지 않는다 |
| 임계값 미설정(`thresholdUsable` 거짓) | 그 종류는 임계선을 그리지 않고 예고도 하지 않는다 |

## 12. 검증

변이 테스트로 **실제로 잡히는지** 확인할 자리:

- `"강수없음"`·`"적설없음"`·`"1mm 미만"` 파싱 (문자열 → 숫자/`null`)
- 폭설 일 누적의 **KST 자정 경계**
- 예고 임계가 `weather_criteria`를 진짜 따르는가 (기준을 바꾸면 예고도 바뀌는가)
- **꺼둔 종류(`enabled=false`)가 예고되지 않는가**
- **카드 색이 예보 때문에 바뀌지 않는가** (3미터 오독 방지)
- `warnings`가 상태 코드를 바꾸지 않는가 / `reasons`는 여전히 503인가
- 예보가 낡았을 때 화면이 그 사실을 말하는가
- 월보드 48시간이 **스크롤 없이** 전부 렌더되는가
- 예보 수집 실패가 마지막 예보를 지우지 않는가

기존 회귀 방지: 발송·승인 경로(`jobs/send.ts`·`remindTick.ts`)의 테스트가 그대로
통과해야 한다. 이 작업은 그 파일들을 건드리지 않는다.

## 13. 열린 항목

- **강수확률(`POP`) 문턱**: 지금 설계는 예보값이 임계 이상이면 확률과 무관하게 예고한다.
  운영해 보고 과경보가 잦으면 `POP` 하한을 두는 것을 검토한다. 지금 넣지 않는 이유는
  실제 빈도를 모르는 채로 문턱을 정하면 근거 없는 숫자가 코드에 박히기 때문이다.
- **예보 정확도 되돌아보기**: 예보와 실제 관측을 비교해 보여주는 화면은 범위 밖이다.
  데이터는 두 테이블에 모두 남으므로 나중에 만들 수 있다.
