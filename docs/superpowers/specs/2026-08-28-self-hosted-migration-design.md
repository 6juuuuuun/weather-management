# 사내 서버 이식 — 설계 문서

- 날짜: 2026-08-28
- 상태: 사용자 검토 대기
- 관련: `docs/superpowers/specs/2026-08-12-weather-management-design.md`

## 1. 목적

외부 SaaS(Supabase·Cloudflare) 의존을 걷어내고, **사내 서버에 도커로 올릴 수 있는
자립형 시스템**으로 이식한다. 회사가 구매하는 서버 워크스테이션에 배포하는 것이 전제다.

이식이지 재개발이 아니다. 특보 판정 엔진, 기상청 수집, 메시지 생성, 웹 화면은 그대로 쓴다.

## 2. 왜 옮기는가

- 직원 개인정보(이름·부서·휴대폰 번호)가 사내에 머문다 — 보안 검토가 쉬워진다
- 외부 SaaS 계약·엔터프라이즈 등급 논의가 사라진다
- 월 고정비가 없어지고 시스템이 회사 자산이 된다
- 사내 서버를 구매하므로 운영 기반이 생긴다

## 3. 구성

컨테이너 **2개**로 간다.

| 컨테이너 | 역할 |
|---|---|
| `postgres` | 데이터, 권한 정책(RLS), 마이그레이션 |
| `app` (Express) | API · 서버 로직 4종 · 인증 · 스케줄러 · 정적 화면 서빙 |

`docker compose up -d` 하나로 뜬다. 인수인계 시 넘길 것은 **compose 파일과 환경변수 파일**이다.

**nginx를 따로 두지 않는다.** Express가 정적 파일을 서빙한다. 사내 배포이므로 HTTPS와
리버스 프록시는 사내 인프라를 쓴다. 사내 표준이 별도 웹서버를 요구하면 컨테이너를
하나 더 얹으면 되고, 그 경우에도 앱 구조는 바뀌지 않는다.

## 4. 무엇이 그대로이고 무엇이 바뀌는가

### 그대로

- **DB 스키마와 권한 정책 14개** — Postgres를 계속 쓰므로 이관만 한다
- 특보 판정 엔진, 기상청 수집, 메시지 템플릿
- 웹 화면 전체(React) — 데이터 접근 계층만 교체
- 알림 채널 인터페이스와 카카오워크 구현

### 바뀌는 것

| 지금 | 이식 후 |
|---|---|
| Supabase PostgREST (`supabase.from(...)`) | Express REST API |
| Supabase Auth | 자체 인증 (§6) |
| Edge Functions (Deno) 4개 | Express 라우트 |
| pg_cron + pg_net | **Express 내부 스케줄러** |
| Cloudflare 정적 호스팅 | Express 정적 서빙 |
| Vault(시크릿) | 환경변수 파일 |

## 5. 권한 정책(RLS)을 유지한다

이 설계에서 가장 중요한 결정이다.

지금 권한은 데이터베이스 안에 있다. 코드에 버그가 있어도 남의 부서 명부가 나가지 않는다.
개인정보를 다루는 시스템에서 이 안전망을 앱 코드로 옮기면, 검사 한 줄을 빠뜨리는 순간
유출로 이어진다. **그래서 옮기지 않는다.**

정책 14개는 `auth.uid()` 하나에 의존한다. 이 함수를 우리가 정의한다.

```sql
create schema if not exists auth;
create or replace function auth.uid() returns uuid
language sql stable as $$
  select nullif(current_setting('app.current_user_id', true), '')::uuid
$$;
```

Express는 요청을 처리할 때마다 트랜잭션 시작 시점에 현재 사용자 ID를 세션에 넣는다.

```
BEGIN;
SET LOCAL app.current_user_id = '<로그인한 사용자의 auth_user_id>';
-- 이후 쿼리에 정책 14개가 그대로 적용된다
COMMIT;
```

`SET LOCAL`이므로 트랜잭션이 끝나면 사라진다. 커넥션 풀에서 값이 다음 요청으로 새지 않는다.

**서버 로직(수집·발송)은 정책을 우회해야 하므로 별도 DB 역할로 접속한다.** 지금
Edge Function이 service role로 도는 것과 같은 구조다.

`auth.users`를 참조하는 1곳은 `employees.auth_user_id`를 직접 쓰도록 정리한다.

## 6. 인증과 회원가입

### 6.1 가입

일반 서비스와 같은 흐름이다. 로그인 화면에서 "계정이 없으신가요?"로 가입 화면에 들어간다.
사내 DNS로만 접근되므로 자유 가입을 허용하되, 두 가지 장치를 둔다.

- **회사 이메일 도메인 제한** — 허용 도메인 목록을 환경변수로 둔다. 외부인 가입을 막는다
- **메일 인증** — 가입 시 인증 링크를 보내고, 클릭해야 계정이 활성화된다

수집 항목: 회사 이메일(아이디로 사용), 비밀번호, 이름, 부서, 휴대폰 번호.

**휴대폰 본인인증은 넣지 않는다.** 건당 비용이 들고, 생년월일·성별 등 필요 없는 개인정보를
추가로 수집하게 된다. 사내 시스템에서 회사 이메일 검증으로 충분하다.

### 6.2 권한

가입한 사람은 기본 `staff`다. **특보 승인 권한과 관리자 권한은 관리자가 별도로 부여한다.**
자유 가입이므로 이 분리가 없으면 누구나 전 직원에게 발송할 수 있게 된다.

### 6.3 세션

**httpOnly 쿠키 + 서버 세션**으로 간다.

현재는 JWT를 브라우저 `localStorage`에 저장한다. 스크립트로 읽을 수 있어 XSS에 노출된다.
httpOnly 쿠키는 스크립트가 읽지 못하고, 로그아웃이나 계정 정지 시 서버에서 즉시 무효화할 수 있다.
옮기는 김에 개선한다.

세션 테이블을 두고 만료를 관리한다. 로그인 성공 시 세션 생성, 로그아웃 시 삭제.

### 6.4 비밀번호

- 저장은 해싱한다. **검증된 라이브러리를 쓰고 암호학을 직접 구현하지 않는다**
- 재설정은 1회용 링크와 만료 시간을 둔다. 사용하면 즉시 무효화한다
- 로그인 반복 실패 시 일시 잠금

### 6.5 메일 발송

가입 인증과 비밀번호 재설정에 메일이 필요하다. **사내 SMTP를 쓰는 것을 기본으로 한다.**
사내 서버에 올리는 시스템이므로 사내 메일 서버 접근이 가능할 가능성이 높다.
IT 담당자에게 SMS 연계와 함께 요청한다.

## 7. 스케줄러

지금은 `pg_cron`이 `pg_net`으로 Edge Function을 HTTP 호출한다. 자체 서버에서는 확장을
두 개 설치하고 DB에서 앱을 부르는 구조가 불필요하게 복잡하다.

**Express 안에서 스케줄러를 돌린다.** 앱 컨테이너가 상시 떠 있으므로 자연스럽고, 확장 설치가
필요 없으며, 실행 로그가 앱 로그에 함께 남는다.

주기는 현행을 유지한다 — 관측 수집 매시 5분, 재알림 점검 10분.

**컨테이너가 재시작해도 중복 실행이나 누락이 없어야 한다.** 마지막 실행 시각을
`heartbeats` 테이블에 기록하고, 기동 시 놓친 주기를 판단한다.

## 8. 알림 채널

**이식 기간에는 카카오워크를 그대로 유지한다.** 채널 코드는 Supabase와 무관하므로 그대로 옮긴다.

이렇게 하면 이식의 완료 기준이 명확해진다 — **기능은 같고 플랫폼만 바뀐 상태**.

SMS 전환은 이식이 끝난 뒤 별도로 진행한다. 사내 발송 시스템 연계 요건은 그때 정리한다.
채널 인터페이스가 이미 분리돼 있어 구현체만 추가하면 된다.

## 9. 운영 장치

이식과 함께 준비한다. 서버에 올리기 전에 있어야 한다.

- **백업** — 매일 덤프를 뜨고 서버 밖에 보관한다. **복구를 한 번 해본다.**
  해보지 않은 백업은 백업이 아니다
- **감시** — 수집이 멈추거나 발송이 실패했을 때 사람이 알아채는 장치.
  관리형 서비스와 달리 자체 서버는 조용히 죽는다. 안전 경보 시스템에서 이것이 최악이다
- **문서** — 배포 절차, 복구 절차, 환경변수 목록

## 10. 단계

| 단계 | 내용 | 하드웨어 필요 |
|---|---|---|
| 1 | 컨테이너 구성 + DB 이관 + 권한 정책 유지 확인 | 없음 |
| 2 | Express API + 서버 로직 4종 이식 + 웹앱 데이터 계층 교체 | 없음 |
| 3 | 인증·회원가입 | 없음 |
| 4 | 스케줄러 + 정적 서빙 + 운영 장치 | 없음 |
| 5 | 서버 배치 · 데이터 이관 · 병행 운영 후 전환 | **필요** |

**4단계까지는 하드웨어 없이 진행한다.** 서버를 사기 전에 문제를 발견하는 것이 목적이다.

각 단계의 완료 기준은 **기존 테스트가 통과하는 것**이다. 지금 114건이 있고, 이식 과정에서
데이터 접근 계층이 바뀌므로 상당수를 고쳐야 한다. 테스트가 줄어들면 이식이 실패한 것이다.

## 11. 범위 밖

- **SMS 연계** — 이식 완료 후 별도 진행
- **알림톡** — 도입하지 않는다
- **행동지침 링크 열람 페이지** — SMS 장문으로 지침 전문을 보내면 불필요하다.
  SMS 전환 시점에 다시 판단한다
- **외부 접근(DMZ·VPN)** — 사내 DNS 배포가 전제다. 조직장이 사외에서 승인해야 하는지가
  확인되면 그때 다룬다
- 개인정보 접속기록 기능 — 필요하지만 이식과 분리해 별도로 다룬다

## 12. 확인이 필요한 사항

1. **조직장이 사외에서 특보를 승인해야 하는가** — 필요하면 외부 접근 설계가 추가된다
2. **사내 SMTP를 쓸 수 있는가** — 가입 인증과 비밀번호 재설정에 필요하다
3. **서버 운영 주체** — 누가 이 서버를 돌보는가
4. **기존 데이터를 옮길 것인가** — 특보 기준·행동지침은 옮기고 발송 이력은 새로 시작하는 것을 권한다
