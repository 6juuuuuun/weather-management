# 날씨경영 운영 안내서

이 문서는 **서버 운영 경험이 없는 사람**이 그대로 따라 할 수 있게 썼습니다.
명령은 통째로 복사해서 붙여 넣으면 됩니다. 모르는 단어가 나오면 §9 용어를 보세요.

**먼저 알아 둘 것 세 가지**

- 이 시스템은 컨테이너 3개로 돌아갑니다: `postgres`(데이터 보관), `migrate`(설치·갱신
  때만 잠깐 도는 1회용), `app`(웹 화면 + API + 자동 수집·발송).
- 모든 명령은 **저장소 폴더 안에서** 실행합니다. 터미널을 열면 먼저 그 폴더로 이동하세요.
  이 문서에서는 그 폴더를 `~/weather`라고 부릅니다.

  ```bash
  cd ~/weather
  ```

- 명령 앞의 `$`나 `#`은 붙여 넣지 마세요. `#`으로 시작하는 줄은 설명입니다.

## 1. 처음 설치하기

### 1-1. 준비물

- 서버(리눅스 또는 macOS) 한 대
- **Docker**와 **Docker Compose**. 아래 명령이 버전을 출력하면 준비된 것입니다.

  ```bash
  docker --version
  docker compose version
  ```

  아무것도 안 나오거나 "command not found"가 뜨면 Docker를 먼저 설치해야 합니다
  (리눅스: `curl -fsSL https://get.docker.com | sh`, macOS: Docker Desktop 설치).
- 기상청 공공데이터포털 인증키와 카카오워크 봇 키(§8 환경변수 표 참고)

**호스트에 PostgreSQL이나 Node.js를 따로 설치할 필요는 없습니다.** 전부 컨테이너 안에 있습니다.

### 1-2. 설정 파일(.env) 만들기

`.env`는 비밀번호와 API 키를 담는 파일입니다. 템플릿을 복사해서 값을 채웁니다.

```bash
cd ~/weather
cp .env.selfhost.example .env
```

비밀번호 세 개는 직접 지어내지 말고 아래 명령으로 만들어서 붙여 넣으세요.
(세 번 실행해서 서로 다른 값 세 개를 얻습니다.)

```bash
openssl rand -hex 24
```

이제 `.env`를 편집기로 열어 값을 채웁니다.

```bash
nano .env      # nano가 없으면 vi .env
```

- `POSTGRES_PASSWORD` — 위에서 만든 임의 문자열 1
- `APP_USER_PASSWORD` — 임의 문자열 2
- `APP_SERVICE_PASSWORD` — 임의 문자열 3
- `APP_BASE_URL` — 사내에서 실제로 접속할 주소. 예: `http://weather.gonjiam.local:8080`
- `KMA_API_KEY` — 기상청 인증키
- `KAKAOWORK_BOT_KEY` — 카카오워크 봇 앱키
- 나머지는 템플릿 그대로 두면 됩니다.

> 비밀번호에 `@ : / # ?` 같은 기호를 넣지 마세요. 접속 주소 문자열에 그대로 들어가서
> 주소가 깨집니다. `openssl rand -hex`는 영문·숫자만 만들어 주므로 안전합니다.
>
> `.env`는 저장소에 올라가지 않습니다(`.gitignore`). 이 파일이 사라지면 데이터베이스에
> 다시 접속할 수 없으니, 안전한 곳에 따로 한 부 복사해 두세요.

### 1-3. 올리기

```bash
cd ~/weather
docker compose up -d --build
```

처음에는 화면을 빌드하느라 5~15분쯤 걸립니다. 두 번째부터는 훨씬 빠릅니다.

이 한 줄이 순서대로 다음을 합니다.

1. `postgres` 컨테이너를 띄우고 데이터베이스가 접속을 받을 때까지 기다립니다.
2. `migrate` 컨테이너가 **스키마(표 구조)를 만들고 기본값을 넣습니다.** 끝나면 스스로 종료합니다.
3. `app` 컨테이너가 뜹니다.

### 1-4. 잘 떴는지 확인

```bash
docker compose ps
```

실제 출력에는 `IMAGE`·`COMMAND`·`SERVICE`·`CREATED`·`PORTS` 칸도 함께 나옵니다.
볼 곳은 **이름과 `STATUS`** 두 칸입니다.

```
NAME                 ...   STATUS
weather-app-1        ...   Up (healthy)
weather-postgres-1   ...   Up (healthy)
```

이름 두 개가 모두 `Up (healthy)`면 정상입니다.

`migrate`는 할 일을 마치고 종료했으므로 **이 목록에는 나오지 않습니다.** 그게 정상입니다.
끝난 컨테이너까지 보려면 `-a`를 붙입니다.

```bash
docker compose ps -a
```

```
NAME                 STATUS
weather-app-1        Up (healthy)
weather-migrate-1    Exited (0)
weather-postgres-1   Up (healthy)
```

`migrate`가 **`Exited (0)`이면 정상**입니다(0 = 오류 없이 끝남).
괄호 안이 0이 아닌 숫자면 마이그레이션이 실패한 것이고, 앱도 뜨지 않습니다 — §7-2를 보세요.

이어서 상태를 확인합니다.

```bash
curl -s localhost:8080/api/health
```

`{"ok":true}`가 나오면 웹 서버가 살아 있는 것입니다.
브라우저에서 `http://서버주소:8080`으로 들어가면 로그인 화면이 보입니다.

### 1-5. 첫 관리자 지정하기 (반드시)

처음 설치한 데이터베이스에는 **관리자가 한 명도 없습니다.** 웹 화면에서 가입하면 누구나
"실무자"로 시작하고, 역할을 올려 줄 수 있는 사람은 관리자뿐이라 그대로 두면 아무도
아무것도 설정할 수 없습니다. 그 매듭을 아래 한 번으로 풉니다.

1. 브라우저에서 `http://서버주소:8080`에 들어가 **회사 이메일로 가입**합니다.
2. 서버 터미널에서 아래를 실행합니다. 이메일은 방금 가입한 것과 철자가 같아야 합니다.

   ```bash
   cd ~/weather
   ./ops/make-admin.sh 본인이메일@gonjiam.com
   ```

   `관리자로 지정했습니다: 본인이메일@gonjiam.com`이 나오면 성공입니다.
3. 웹 화면에서 **로그아웃했다가 다시 로그인**합니다. 관리자 메뉴가 보입니다.

> 이 명령은 두 번째 관리자를 만들 때도 그대로 씁니다. 다만 관리자가 한 명이라도 있으면
> 그 다음부터는 웹 화면의 **직원 관리**에서 역할을 바꾸는 편이 낫습니다.

**"데이터베이스(postgres) 컨테이너를 찾지 못했습니다"가 나오면** 스택을 기본 이름이
아닌 다른 compose 프로젝트 이름으로 올린 것입니다(`docker compose -p 이름 up` 또는
`COMPOSE_PROJECT_NAME`). 같은 이름을 주고 다시 실행하세요:

```bash
COMPOSE_PROJECT_NAME=프로젝트이름 ./ops/make-admin.sh 본인이메일@gonjiam.com
```

떠 있는 프로젝트 이름은 `docker compose ls`로 볼 수 있습니다. **가입을 다시 할 필요는
없습니다** — 가입은 정상이고, 스크립트가 데이터베이스에 닿지 못한 것뿐입니다.

### 1-6. 설치 직후 반드시 입력해야 하는 것 (안 하면 발송이 비어 나갑니다)

`migrate`가 넣어 주는 기본값은 **부서 트리·특보 기준·알림 설정**까지입니다.
**부서별 행동지침은 비어 있습니다** — 시스템이 자동으로 만들어 낼 수 없는, 조직마다
다른 내용이기 때문입니다. **비워 두면 메시지가 "무엇을 하라" 없이 나가는 것이 아니라
아예 나가지 않습니다** — 지침이 곧 발송 대상(부서)이라 초안이 통째로 비고, 승인 화면의
승인 버튼도 눌리지 않습니다. `/api/health/deep`도 그 상태를 사유로 알려 줍니다(§3-3).
관리자로 로그인한 뒤 대시보드의 **셋업 체크리스트**를 순서대로 끝내세요.

1. **관측 지점** — 위쪽 메뉴 **알림 설정** → `관측 지점` 카드에서 지점 이름·주소와
   기상청 격자좌표(nx, ny)를 입력합니다. **좌표를 잘못 넣으면 날씨 수집이 통째로
   멈춥니다** — nx는 1~149, ny는 1~253 범위여야 하고, 벗어난 값은 화면과 서버가
   모두 거부합니다. 이미 잘못된 값이 들어가 있다면 `/api/health/deep`(§3-3)이
   좌표를 그대로 실어 사유로 알려 줍니다
2. **특보 기준** — 4종(폭우·폭설·강풍·폭염) × 2등급 임계값 확인·조정 (기본값이 들어 있습니다)
3. **부서 구성** — 직원 관리 화면의 부서 관리에서 부서 트리 확인·수정 (기본 트리가 들어 있습니다).
   **단 수 제한은 없습니다** — 부서 아래에 부서를 몇 단이든 만들 수 있고, 화면은 만들어 둔
   깊이 그대로 그립니다. 행동지침과 부서 수신자는 **더 이상 하위 부서가 없는 부서**(말단)에만
   답니다 — 최상위 부서를 하위 부서 없이 하나만 만들면 그 부서 자체가 말단입니다.
   조직 개편으로 부서를 다른 부서 밑으로 옮겨야 하면, 부서 관리의 **상위 부서** 칸에서
   바꾸세요. **지우고 새로 만들지 마세요** — 지우면 그 부서의 행동지침과 수신자 지정이
   함께 사라지지만, 옮기면 그대로 따라갑니다.
4. **부서별 지침** — 위쪽 메뉴 **행동 지침**에서 종류 × 등급 × 부서마다 인력 조정 지침과
   고객 안내 멘트를 입력합니다. **여기가 비어 있으면 안 됩니다.** 지침을 등록한 부서에는
   **부서 수신자**도 반드시 지정하세요 — 지침만 있고 수신자가 없으면 그 부서 몫은
   0명에게 나갑니다(체크리스트의 `부서 수신자` 항목이 이것을 봅니다).
   지침 한 항목은 200자까지, 한 부서·종류·등급에 20개까지, 고객 안내 멘트는
   1000자까지입니다 — 이 값들은 카카오워크 DM 본문에 그대로 실리므로 상한이 있습니다.
   더 이상 쓰지 않는 지침은 그 화면의 **지침 삭제**로 지웁니다 — 내용만 비워 두면
   "등록되지 않음"으로 세어져 체크리스트가 다시 미완료가 되고, 지침을 지우면 그 부서는
   해당 종류·등급의 발송 대상에서 빠집니다(부서 수신자 지정은 그대로 남습니다).
5. **Alert 수신자** — 위쪽 메뉴 **특보 기준** → 맨 아래 `특보 Alert 수신자` 카드에서
   지정합니다. 특보 발생 시 승인 알림을 받을 사업부장입니다.
   여기에 아무도 없으면 특보가 감지돼도 **승인할 사람에게 알림이 가지 않고**,
   §5의 자동 점검 알림도 받을 사람이 없습니다.

   > **승인 권한은 오직 이 목록에서 나옵니다 — 역할과 아무 관계가 없습니다.**
   >
   > 이 목록에 있는 사람만 특보 초안을 승인·발송할 수 있습니다. 역할(관리자·승인자·
   > 실무자)은 **어느 화면을 볼 수 있는가**만 정합니다. 그래서 이렇게 됩니다.
   >
   > - 역할을 `승인자`로 올려도 **승인 권한은 생기지 않습니다.** 이 목록에 넣어야 합니다.
   > - 역할이 `실무자`인 사람도 이 목록에 있으면 **승인할 수 있습니다.**
   > - 인사이동으로 승인 권한을 **회수**하려면 역할을 낮추는 것이 아니라
   >   **이 목록에서 빼야 합니다.** 역할만 낮추면 그 사람은 계속 승인할 수 있습니다.
   >
   > 승인 요청 DM을 받는 사람과 승인할 수 있는 사람이 정의상 같아야 하기 때문에
   > 이렇게 정했습니다(두 목록이 어긋나 승인이 멈춘 사고가 있었습니다).
   > 이 목록에 사람을 넣는 것은 **곧 승인·발송 권한을 주는 일**입니다.
6. **카카오워크 연결** — 지정한 Alert 수신자가 실제로 카카오워크에 연결돼 있어야 합니다.
   직원 관리 화면의 **카카오워크** 칸이 "연결됨"인지 보세요.

7. **실제 발송** — 서버 `.env`의 `NOTIFY_CHANNEL`이 **비어 있어야** 합니다.
   `console`로 두면 카카오워크로 아무것도 나가지 않고 **앱 로그에만** 찍힙니다.
   이 값은 설치 점검·시연에서 진짜 직원에게 DM이 가지 않게 하려고 일부러 쓰는 값이고,
   그 용도로는 정상입니다. 위험한 것은 **그 상태로 운영을 시작하는 것**입니다 —
   봇 키가 유효하면 직원들의 카카오워크 연결은 전부 "연결됨"이 되고, 위의 1~6번이
   전부 초록이 되고, 승인을 눌러도 `발송 1명`으로 성공한 것처럼 보입니다.
   **그런데 그 DM은 전부 로그 파일로 갑니다.** 리허설·시연에 쓰던 `.env`를 실서버로
   복사할 때 이 한 줄이 따라오는 것이 가장 흔한 경로입니다.
   지금 어느 쪽인지는 이렇게 확인합니다.

   ```bash
   cd ~/weather
   grep NOTIFY_CHANNEL .env          # 값이 비어 있어야 합니다
   curl -s localhost:8080/api/health/deep | grep -o "로그 전용" || echo "실채널"
   ```

   `로그 전용`이 나오면 `.env`에서 `NOTIFY_CHANNEL=` 을 빈 값으로 고치고
   `KAKAOWORK_BOT_KEY`를 채운 뒤 `docker compose up -d`로 다시 올리세요.
   체크리스트의 `실제 발송` 항목과 `/api/health/deep`이 같은 것을 봅니다.

#### 6번(카카오워크 연결)이 안 될 때

연결은 서버가 **회사 이메일로 카카오워크 사용자를 찾아** 자동으로 채웁니다. 채워지는
때는 네 가지입니다: 가입할 때 / 관리자가 직원을 등록할 때 / 관리자가 이메일을 고칠 때 /
**매일 새벽 5시 20분**(그때까지 미연결인 사람을 다시 찾아봅니다).

"미연결"로 남는다면 보통 아래 셋 중 하나입니다.

| 원인 | 확인 | 조치 |
|---|---|---|
| `.env`의 `KAKAOWORK_BOT_KEY`가 비어 있다 | 앱 로그에 `봇 키가 없어 ... 건너뜁니다` | 키를 넣고 `docker compose up -d` |
| 카카오워크 계정 이메일이 회사 이메일과 다르다 | 앱 로그에 `...에 해당하는 카카오워크 사용자를 찾지 못했습니다` | 직원 관리에서 이메일을 고치거나, 관리자가 카카오워크 ID를 직접 입력 |
| 카카오워크 계정이 아직 없다 | 같은 로그 | 계정을 만든 뒤 새벽 재시도를 기다리거나 이메일을 한 번 저장 |

**이 항목이 왜 중요한가:** 특보 승인 요청·재알림·자동 점검 알림이 전부 이 연결을
통해 나갑니다. 연결된 사람이 0명이면 **특보를 정상적으로 감지해도 아무에게도
전달되지 않습니다.** 그래서 체크리스트와 `/api/health/deep`이 이 상태를 따로 봅니다.

## 2. 매일 쓰는 명령

| 하고 싶은 일 | 명령 |
|---|---|
| 상태 보기 | `docker compose ps` |
| 앱만 껐다 켜기 | `docker compose restart app` |
| 전체 껐다 켜기 | `docker compose restart` |
| 로그 실시간 보기 (Ctrl+C로 빠져나옴) | `docker compose logs -f app` |
| 최근 로그 200줄만 보기 | `docker compose logs --tail 200 app` |
| 전체 내리기 (데이터는 남습니다) | `docker compose down` |
| 다시 올리기 | `docker compose up -d` |

> **`docker compose down -v`는 절대 쓰지 마세요.** `-v`는 데이터베이스 볼륨까지
> 지웁니다 — 직원 명부·발송 이력·설정이 전부 사라집니다. `down`만 쓰면 데이터는 남습니다.

### 코드를 새 버전으로 올릴 때

```bash
cd ~/weather
git pull
docker compose up -d --build
```

`migrate`가 알아서 새 스키마 변경만 적용합니다(이미 적용한 것은 건너뜁니다).
올리기 전에 §4의 백업을 한 번 떠 두면 안전합니다.

#### 기본 데이터(부서 트리·특보 기준)는 첫 설치 때 한 번만 들어갑니다

업데이트할 때 기본 데이터를 다시 넣지 않습니다. **화면에서 지운 부서나 이름을 바꾼
부서가 업데이트로 되살아나지 않습니다.** 로그에는 이렇게 나옵니다.

```
기본 데이터(seed)는 첫 설치 때 이미 들어갔습니다 — 건너뜁니다.
```

기본 부서 구성이나 특보 기준을 조직에 맞게 고쳤다면 그대로 유지됩니다 —
안심하고 지우고 바꾸셔도 됩니다.

### 서버를 재부팅하면 (윈도우 업데이트·정전)

**아무것도 안 하셔도 됩니다.** 도커가 다시 시작되면 `postgres`와 `app`이 스스로
되살아납니다(둘 다 `restart: unless-stopped`). 데이터는 볼륨에 남아 있습니다.

`migrate` 컨테이너만 다시 뜨지 않습니다 — **정상입니다.** 스키마는 이미 적용돼
있고, 새 스키마 변경은 다음 `docker compose up -d --build` 때 들어갑니다.
`docker compose ps`에 `migrate ... Exited (0)`로 보이는 것이 맞는 모습입니다.

재부팅 5분 뒤에 §3-3(`/api/health/deep`)을 한 번 확인해 주세요. 재부팅 직후에는
수집이 한 주기 밀릴 수 있는데, 앱이 뜨면서 스스로 한 번 따라잡습니다
(마지막 수집이 70분 넘게 지났으면 기동 시 바로 한 번 수집합니다).

> 예전에는 `postgres`에 재시작 설정이 없어서 재부팅하면 **앱만 살아났습니다.**
> 그때가 가장 위험한 상태였습니다: `docker compose ps`는 `Up (healthy)`이고
> `/api/health`도 200인데, 화면의 모든 기능이 오류가 나고 점검 알림조차
> 나가지 않습니다. 지금은 그렇게 되지 않습니다.

## 3. 상태 확인하기

확인 방법이 세 가지 있고, 각각 보는 것이 다릅니다.

### 3-1. `docker compose ps` — 컨테이너가 살아 있는가

```bash
docker compose ps
```

`STATUS` 칸의 뜻:

| 표시 | 뜻 | 할 일 |
|---|---|---|
| `Up (healthy)` | 정상 | 없음 |
| `Up (health: starting)` | 방금 떠서 확인 중 | 1분 기다렸다 다시 봅니다 |
| `Up (unhealthy)` | 웹 서버가 응답을 못 함 | §7-4 |
| `Exited (0)` | 정상적으로 끝남 (`migrate`는 이게 정상) | 없음 |
| `Exited (숫자)` | 오류로 죽음 | §7-1 |
| `Restarting` | 계속 죽고 되살아나는 중 | §7-1 |

> **중요 1 — `healthy`를 믿지 마세요.** 이 `healthy` 표시는 "웹 서버가 응답하는가"만
> 봅니다(§3-2와 같은 것을 봅니다). **데이터베이스가 통째로 죽어 있어도 `Up (healthy)`로
> 보입니다.** 실제로 확인했습니다: postgres 컨테이너를 내려도 app은 계속
> `Up (healthy)`였고, 그 상태에서 화면의 거의 모든 기능이 동작하지 않았습니다.
> **시스템이 실제로 일을 하고 있는지는 §3-3으로만 알 수 있습니다.**
>
> **중요 2 — Docker는 `unhealthy`를 보고도 아무것도 하지 않습니다.** 컨테이너를 대신
> 재시작해 주지 않습니다. `restart: unless-stopped` 설정은 "프로세스가 완전히 죽었을 때"만
> 다시 띄웁니다. `unhealthy`는 사람에게 보여 주는 표시일 뿐이라, 사람이 보고
> 조치해야 합니다(§7-4).

### 3-2. `/api/health` — 웹 서버가 응답하는가

```bash
curl -s localhost:8080/api/health
```

`{"ok":true}`면 프로세스가 응답한다는 뜻입니다. **이것만으로는 부족합니다** —
데이터베이스가 죽어 있어도, 수집이 몇 시간째 멈춰 있어도 이 값은 `true`입니다.
`docker compose ps`의 `healthy` 표시도 바로 이 값을 보고 붙는 것이라 같은 한계가 있습니다.

### 3-3. `/api/health/deep` — 시스템이 실제로 일을 하고 있는가

**이게 진짜 확인입니다.** 하루 한 번쯤 보면 좋습니다.

```bash
curl -s localhost:8080/api/health/deep
```

정상일 때:

```json
{"ok":true,"reasons":[]}
```

문제가 있을 때(HTTP 상태 코드도 503으로 바뀝니다):

```json
{"ok":false,"reasons":["관측 수집이 130분 넘게 멈춰 있습니다"]}
```

나올 수 있는 `reasons`와 뜻:

| 문장 | 뜻 | 할 일 |
|---|---|---|
| `관측 수집이 130분 넘게 멈춰 있습니다` | 매시 한 번 도는 기상 수집이 2회 이상 연속으로 안 돌았습니다. 지금 폭우가 와도 특보가 안 뜹니다. | §7-3 |
| `최근 3회 관측이 모두 결측입니다` | 수집은 도는데 기상청에서 값이 안 옵니다. 인증키 만료나 관측소 점검일 수 있습니다. | §7-3 |
| `최근 3회 관측이 수집은 됐지만 값이 전부 비어 있습니다 (기상청 응답 형식이 바뀌었을 수 있습니다)` | 수집도 되고 결측도 아닌데 값만 전부 없습니다. 기상청이 응답 형식(항목 이름)을 바꿨을 때 이렇게 됩니다. 이 상태에서는 폭우가 와도 특보가 뜨지 않습니다. | 개발 담당자에게 연락하세요 |
| `관측 지점 좌표(nx=..., ny=...)가 기상청 격자 범위를 벗어났습니다 (nx 1~149, ny 1~253) — 날씨 수집이 계속 실패합니다. 알림 설정에서 좌표를 고쳐 주세요` | 저장된 좌표가 기상청 격자 밖이라 수집 호출이 매시간 실패합니다. 화면에는 아무 티도 나지 않고 수집만 멈춥니다. | **알림 설정 → 관측 지점**에서 좌표를 고치세요(nx 1~149, ny 1~253) |
| `Alert 수신자 N명 중 카카오워크에 연결된 사람이 0명입니다 — 특보가 아무에게도 전달되지 않습니다` | 수신자는 지정돼 있는데 아무도 카카오워크로 연결되지 않았습니다. 특보가 감지돼도 아무에게도 전달되지 않습니다. | §1-6의 6번 |
| `특보 승인 요청을 받을 Alert 수신자가 한 명도 지정되어 있지 않습니다` | 승인 알림을 받을 사람이 없습니다. | §1-6의 5번 |
| `최근 3회 관측에서 강수량·기온·... 항목만 계속 비어 옵니다 (기상청 항목 이름이 바뀌었을 수 있습니다) — 그 항목으로 판정하는 특보가 뜨지 않습니다` | 기상청 응답의 **일부 항목만** 죽었습니다. 예를 들어 강수량 하나가 비면 폭우와 폭설이 동시에 뜨지 않습니다(둘 다 강수 항목으로 판정합니다). 다른 값은 정상이라 화면으로는 알 수 없습니다. | 개발 담당자에게 연락하세요 |
| `마지막 수집·판정이 실패로 끝났습니다 (...)` | 앱이 스스로 "이번에 실패했다"고 기록해 둔 상태입니다. 괄호 안이 `missing`이면 기상청 응답을 못 받은 것이고, `action-failed:...`면 특보 처리 중 오류입니다. | §7-3 · 개발 담당자 |
| `알림 설정의 특보 4종이 모두 꺼져 있습니다 — 어떤 날씨에도 특보가 뜨지 않습니다` | 알림 설정에서 폭우·폭설·강풍·폭염을 전부 꺼 두었습니다. 어떤 날씨에도 특보가 뜨지 않습니다. | 설정 → 알림 설정에서 필요한 종류를 켜세요 |
| `내용이 있는 행동지침이 한 건도 없습니다 — 특보가 떠도 발송할 부서·내용이 만들어지지 않습니다` | 부서별 행동지침이 없거나 전부 내용이 비어 있습니다. 특보가 떠도 보낼 내용과 대상이 만들어지지 않아 **승인해도 아무에게도 가지 않습니다.** | §1-6의 4번(행동지침 등록) |
| `지침은 있는데 수신자가 한 명도 없는 부서가 N곳입니다 — 그 부서 몫은 0명에게 발송됩니다` | 그 부서 몫은 0명에게 발송됩니다. 승인 화면에도 같은 경고가 뜹니다. **N은 부서 수입니다**(지침 건수가 아닙니다). | **행동 지침** 화면에서 그 부서를 고르고 `수신 담당자`에 사람을 지정하세요 |
| `지침과 수신자는 있는데 카카오워크에 연결된 수신자가 한 명도 없는 부서가 N곳입니다 — 그 부서 몫은 승인해도 0명에게 발송됩니다` | 수신자를 **지정은 했는데** 그 사람들이 아무도 카카오워크에 연결되어 있지 않습니다. 승인 버튼은 정상으로 보이고, 누른 뒤에야 "0명 발송"을 알게 됩니다. | **행동 지침** 화면에서 그 부서의 수신자 칩에 `카카오워크 미연결`이 붙은 사람을 확인하고 §1-6의 6번으로 연결하세요 |
| `승인 대기 중인 특보 N건이 최대 M시간째 승인되지 않았습니다 (재알림 6회를 다 보내고 멈춘 상태입니다) — 대시보드에서 승인하거나 무시 처리해 주세요` | 초안이 승인되지 않아 **아무에게도 나가지 않은** 특보가 열려 있습니다. 재알림은 이미 멈췄거나(§5-1) 아예 돌지 않고 있습니다. | 대시보드에서 승인하거나 무시하세요. 승인할 사람이 없으면 §5-1 |
| `특보 기준 값이 잘못돼 판정할 수 없는 항목이 있습니다: 폭우 주의보 — 그 종류는 어떤 날씨에도 특보가 뜨지 않습니다. 특보 기준 화면에서 값을 다시 저장해 주세요` | 저장된 임계값의 항목 이름이 다르거나 0 이하입니다. 그 종류는 판정 자체가 되지 않는데 화면에는 빈칸으로만 보입니다. | **특보 기준** 화면에서 그 종류의 값을 넣고 저장하세요(저장할 때 값 검사를 통과해야 합니다) |
| `발송 채널이 로그 전용(console)입니다 — 카카오워크에 연결된 수신자 N명이 있는데 모든 특보 DM이 사람 대신 앱 로그로만 나갑니다. 서버 .env에서 NOTIFY_CHANNEL을 비우고 KAKAOWORK_BOT_KEY를 채운 뒤 다시 올려 주세요` | **모든 특보가 사람이 아니라 로그 파일로 나가고 있습니다.** 화면은 전부 정상으로 보이고 승인도 "발송 1명"으로 성공한 것처럼 보이는데, 실제로 받은 사람은 아무도 없습니다. 시연·설치 점검용 설정(`NOTIFY_CHANNEL=console`)이 운영에 남았거나 `KAKAOWORK_BOT_KEY`가 비어 있을 때 이렇게 됩니다. | §1-6의 7번 — `.env`에서 `NOTIFY_CHANNEL=` 을 빈 값으로 두고 `KAKAOWORK_BOT_KEY`를 채운 뒤 `docker compose up -d` |
| `데이터베이스에 연결할 수 없습니다 (...)` | 앱은 살아 있는데 데이터베이스에 못 닿습니다. | §7-4 |

**설치 직후**에는 앱이 뜨자마자 수집을 한 번 따라잡으므로 보통 곧바로 `ok:true`가
나옵니다(실제 설치에서 확인). 몇 분이 지나도 `관측 수집이 ... 멈춰 있습니다`가 사라지지
않으면 기상청 인증키(`KMA_API_KEY`)부터 의심하세요 — §7-3입니다.

### 3-4. 관제실 벽걸이 화면 (월보드)

대시보드 오른쪽 위의 **전체화면** 버튼을 누르면 네비게이션과 조작 버튼이 빠진
관망 전용 화면이 됩니다. 주소 끝에 `?board=1`이 붙습니다.

```
http://<서버주소>:8080/?board=1
```

**벽걸이 기기에는 이 주소를 그대로 북마크해 두세요.** 기기가 재부팅돼도 브라우저가
바로 이 화면으로 들어옵니다. 화면은 30초마다 스스로 값을 다시 받아 오고, 시계는
10초마다 갱신합니다. `ESC`로 전체화면을 빠져나오면 일반 대시보드로 돌아옵니다.

#### 로그인은 한 번만 하면 됩니다

월보드도 로그인이 필요합니다(사내망이라도 직원 이름·부서가 화면에 실립니다).
**한 번 로그인해 두면 화면이 켜져 있는 한 다시 로그인할 필요가 없습니다** —
세션은 마지막 활동으로부터 8시간이고, 30초마다 도는 화면 자체가 그 활동이 됩니다.

> 예전에는 세션이 12시간 고정이라 **하루 두 번 사람이 가서 로그인해야 했고**, 꺼지는
> 시각도 마지막 로그인 시각에 따라 제멋대로였습니다(새벽에 로그인 폼이 걸린 채로
> 아침을 맞는 일이 있었습니다). 지금은 그렇게 되지 않습니다.

반대로 **화면이 꺼져 있거나 브라우저가 닫혀 있으면 8시간 뒤에 만료됩니다.**
월보드가 오래 꺼져 있었다면 다시 켤 때 한 번 로그인해 주세요.
월보드용 계정은 **읽기만 하는 일반 직원(staff) 역할**로 따로 하나 만들어 쓰는 것을
권합니다 — 관리자 계정을 벽에 띄워 두지 마세요.

#### 화면이 멈췄는지는 화면이 스스로 말합니다

월보드는 값이 낡거나 서버에 못 닿으면 **그 사실을 가장 큰 글씨로 먼저 말합니다.**
숫자만 남기고 조용히 멈추지 않습니다.

| 화면에 보이는 것 | 뜻 | 할 일 |
|---|---|---|
| 왼쪽 위 `평온` / `특보 발생` / `대응 중` | 정상입니다. 값이 최신이라는 뜻이기도 합니다. | — |
| 왼쪽 위 `수집 중단` + 빨간 띠 `아래 값은 갱신되지 않고 있습니다` | 마지막 관측이 100분을 넘겼습니다. 지금 폭우가 와도 특보가 뜨지 않는 상태입니다. | §3-3을 확인하고 §7-3 |
| 왼쪽 위 `연결 끊김` + 빨간 띠 `서버 연결 끊김` | 화면이 서버에서 값을 받아 오지 못하고 있습니다(앱 재기동 중이거나 데이터베이스가 죽었거나 세션이 만료됐습니다). | §7-4 |
| 오른쪽 위 수집 시각이 빨갛고 `· 3일 전`이 붙음 | 언제 관측이었는지를 그대로 적은 것입니다. | 위와 같음 |

띠가 떠 있는 동안에도 아래 숫자는 **마지막으로 받아 둔 값**이 그대로 남습니다 —
일부러 그렇게 둡니다. 다만 그 값이 지금 날씨가 아니라는 것을 띠가 말해 줍니다.

## 4. 백업과 복구

### 4-1. 백업 한 번 떠 보기

백업 파일을 둘 폴더를 정하고(서버가 통째로 죽는 상황이 백업을 꺼내 쓰는 상황이므로
**되도록 다른 디스크나 NAS**로 잡으세요), 폴더를 만든 뒤 실행합니다.

`/backup` 같은 최상위 경로는 관리자 권한이 필요하므로 `sudo`를 붙이고, 폴더 주인을
지금 로그인한 사용자로 바꿔 둡니다(안 바꾸면 크론이 돌 때 쓰기 권한이 없습니다).

```bash
sudo mkdir -p /backup/weather
sudo chown "$USER" /backup/weather
cd ~/weather
BACKUP_DIR=/backup/weather ./ops/backup.sh
```

> 서버에 별도 디스크가 없어 홈 폴더 밑에 두겠다면 `sudo` 없이 `mkdir -p ~/backup/weather`로
> 만들고, 아래 명령의 `/backup/weather`를 `~/backup/weather`로 바꿔 읽으세요.
> 다만 **서버가 통째로 죽으면 그 폴더도 함께 사라진다**는 점은 알고 있어야 합니다.

성공하면 이렇게 나옵니다.

```
백업 완료(검사 통과): /backup/weather/weather-20260901-030012.sql.gz (1927265바이트)
```

**"(검사 통과)"가 붙어야 진짜 성공입니다.** 스크립트는 파일을 만든 뒤
① 덤프 프로그램이 오류 없이 끝났는지 ② 파일이 손상되지 않았는지 ③ 덤프가 끝까지
쓰였고 직원·부서 같은 필수 테이블이 실제로 담겼는지를 확인하고, 하나라도 어긋나면
**파일을 남기지 않고** 오류로 끝냅니다. 반쯤 만들어진 파일이 정상 백업 이름으로
남는 것이 가장 위험하기 때문입니다 — 그것이 가짜라는 사실은 복구가 필요한 바로
그 순간에 밝혀집니다.

파일 이름의 숫자는 `연월일-시분초`입니다(`weather-20260901-030012.sql.gz` = 9월 1일 3시 0분 12초).
같은 날 여러 번 떠도 서로 덮어쓰지 않습니다.

30일이 지난 백업 파일은 자동으로 지워집니다(디스크가 차면 어느 날 데이터베이스가
멈춥니다). 오늘 백업이 실패하면 이 정리도 건너뛰므로, 멀쩡한 예전 백업이 사라지지 않습니다.
백업 도중에 서버가 꺼지면 `.partial`로 끝나는 찌꺼기 파일이 남을 수 있는데, 다음 백업이
알아서 치웁니다(하루가 지난 것만 지우므로 진행 중인 백업은 건드리지 않습니다).
`.partial` 파일은 **복구에 쓸 수 없습니다** — 이름이 다른 이유가 그것입니다.

### 4-2. 매일 새벽 자동 백업 걸기

```bash
crontab -e
```

편집기가 열리면 맨 아래에 아래 두 줄을 붙여 넣고 저장합니다
(`/home/사용자/weather` 부분은 실제 저장소 경로로 바꾸세요).

```
0 3 * * * cd /home/사용자/weather && BACKUP_DIR=/backup/weather ./ops/backup.sh >> /backup/weather/backup.log 2>&1
30 3 * * 1 cd /home/사용자/weather && ls -t /backup/weather/weather-*.sql.gz | head -1 | xargs ./ops/verify-backup.sh >> /backup/weather/backup.log 2>&1
```

- 첫 줄: 매일 새벽 3시에 백업을 뜨고 결과를 `backup.log`에 남깁니다.
- 둘째 줄: 매주 월요일 새벽 3시 30분에 **가장 최근 백업 파일을 다시 검사**해서
  결과를 같은 로그에 남깁니다.

#### 백업이 잘 되고 있는지 확인하는 법 (한 달에 한 번)

**1) 로그에 실패가 없는지 봅니다.**

```bash
grep -c "백업 완료(검사 통과)" /backup/weather/backup.log   # 성공한 날 수
grep    "백업 실패"            /backup/weather/backup.log   # 실패한 날 (아무것도 안 나와야 정상)
```

`백업 실패`가 한 줄이라도 있으면 그날 백업은 **없는 것**입니다(파일도 남기지 않습니다).
왜 실패했는지가 바로 그 줄 위에 적혀 있습니다 — 대개 디스크가 찼거나 컨테이너가 내려가 있습니다.

**2) 실제 파일을 직접 검사합니다.** 로그만 믿지 말고 파일을 열어 확인하는 쪽이 확실합니다.

```bash
cd ~/weather
./ops/verify-backup.sh /backup/weather/weather-20260901-030012.sql.gz
```

```
✅ 쓸 수 있는 백업입니다: /backup/weather/weather-20260901-030012.sql.gz
   테이블 16개, 1927265바이트
```

`❌`가 나오면 **그 파일로는 복구할 수 없습니다.** 다른 날짜 파일을 몇 개 더 검사해서
쓸 수 있는 것이 있는지 확인하고, 없으면 곧바로 `./ops/backup.sh`로 새로 뜨세요.

**3) 파일 크기와 개수를 훑어봅니다.**

```bash
ls -lh /backup/weather/
```

크기가 갑자기 확 줄어든 날이 있으면 그 파일을 2)로 검사해 보세요.

> **"파일이 있고 크기가 크다"는 백업이 성공했다는 뜻이 아닙니다.** 덤프가 중간에
> 끊기면 앞쪽 테이블만 담긴 수 MB짜리 파일이 남습니다. 실제로 직원과 부서가 통째로
> 빠진 9.8MB 파일이 "정상 백업"으로 저장된 적이 있어, 지금은 스크립트가 그것을
> 걸러냅니다. 그래도 확인은 위 2)번으로 하세요 — 크기로 판단하지 마세요.

### 4-3. 복구하기

> 지금 들어 있는 데이터가 전부 사라지고 백업 시점으로 돌아갑니다.
> 복구 중에는 앱이 잠깐 멈춥니다(스크립트가 알아서 내렸다가 올립니다).

먼저 어떤 백업이 있는지 봅니다.

```bash
ls -lh /backup/weather/
```

되돌릴 파일을 골라 실행합니다.

```bash
cd ~/weather
./ops/restore.sh /backup/weather/weather-20260901-030012.sql.gz
```

스크립트가 **먼저 그 파일을 검사합니다.** 쓸 수 없는 파일이면 데이터베이스를 건드리기
전에 멈춥니다(지금 들어 있는 데이터는 그대로 남습니다). 검사를 통과하면 5초 동안
취소할 기회를 주고(Ctrl+C), 그 뒤 복구가 진행되고 앱이 다시 뜹니다.
끝나면 확인합니다.

```bash
curl -s localhost:8080/api/health/deep
```

**백업은 복구를 해 봐야 백업입니다.** 실제 운영 데이터로 연습하지 말고,
반기에 한 번쯤 별도 서버나 별도 폴더에 복사해서 복구가 되는지 확인하세요.

## 5. 자동으로 오는 점검 알림

앱이 **6시간마다 스스로 상태를 점검**합니다(§3-3과 같은 내용을 봅니다).
문제가 있을 때만 **Alert 수신자로 지정된 사람들에게 카카오워크 DM**이 갑니다.

```
[날씨경영 점검]
관측 수집이 130분 넘게 멈춰 있습니다
```

정상일 때는 아무 메시지도 오지 않습니다 — 6시간마다 오는 "정상입니다"를 사람이 곧
무시하기 시작하면, 진짜 사고 메시지도 함께 묻히기 때문입니다.

> **이 알림을 받으려면 Alert 수신자가 최소 한 명 지정돼 있고, 그 사람이 카카오워크에
> 연결돼 있어야 합니다**(§1-6의 5번·6번). 아무도 없으면 문제가 생겨도 아무에게도
> 가지 않습니다.
>
> 연결된 사람이 0명일 때는 **그 사실 자체가 카카오워크로 알릴 수 없는 상태**입니다.
> 그래서 앱은 서버 로그에 `[watchdog] 점검에서 문제를 찾았지만 알릴 대상이 없습니다`를
> 남기고, 대시보드 셋업 체크리스트와 `/api/health/deep`(503)이 그 상태를 보여 줍니다.
> 카카오워크 알림에만 기대지 말고 §3-3을 하루 한 번 보시는 이유가 이것입니다.

> **반복 발송과 해제 알림은 매 회차 부서 수신자 명단을 다시 읽습니다.** 그래서 승인 화면에서
> 그 발송에 한해 사람을 빼거나 더한 것은 **1회차에만** 반영되고, 2회차부터는 **행동 지침**
> 화면의 수신 담당자 명단이 그대로 쓰입니다. 일부러 그렇게 돼 있습니다 — 야간 교대가
> 일어나면 지금 근무 중인 사람이 받아야 하고, 승인 시점에 찍어 둔 명단으로 계속 보내면
> 퇴근한 사람만 받게 됩니다. **명단을 오래 바꾸려면 행동 지침 화면에서 바꾸세요.**

### 5-1. 승인 재알림과 그 종료

특보 초안이 승인되지 않으면 **Alert 수신자에게 30분마다**(설정의 재알림 주기) 재촉 DM이
갑니다. 메시지에는 그 시점의 관측값이 함께 들어 있어 링크를 열지 않고도 상황을 볼 수 있습니다.

**재알림은 6회에서 멈춥니다**(기본 주기 30분 기준 약 3시간). 그 시점에 **관리자 역할
계정들에게** 별도 DM이 갑니다.

```
[날씨경영] 폭우 주의보 초안이 약 3시간(재알림 6회) 동안 승인되지 않았습니다.
승인 권한자가 응답하지 않고 있어 재알림을 멈춥니다 — 직접 확인해 주세요.
```

이 메시지를 받으면 **초안이 아직 승인되지 않은 상태 그대로**라는 뜻입니다. 승인 권한자가
자리를 비웠다면 **특보 기준** 화면의 `특보 Alert 수신자`에 한 명 더 넣거나
(그 목록에 들어가는 즉시 승인 권한이 생깁니다 — §1-6의 5번) 대신 승인할 사람을 정하세요. 관리자가 카카오워크에 연결돼 있지 않으면 이 메시지도 갈 곳이
없어 서버 로그에만 남습니다.

**재알림이 멈춰도 그 특보가 감시에서 사라지지는 않습니다.** 상한에 도달했거나 재알림
자체가 돌지 않아 오래 방치된 초안이 있으면 `/api/health/deep`이 503과 함께
`승인 대기 중인 특보 N건이 최대 M시간째 승인되지 않았습니다`를 돌려주고, 6시간마다 도는
점검(§5)이 같은 문장을 Alert 수신자에게 DM으로 보냅니다 — **30분마다 두드리던 것이
6시간마다로 느려질 뿐, 조용해지지는 않습니다.** 조용한 실패는 이 시스템에서 가장 위험한
상태이고, 상한은 그것을 만들려고 넣은 값이 아닙니다.

## 6. 계정 문제 해결하기

### 6-1. 직원이 비밀번호를 잊었을 때

관리자가 웹 화면의 **직원 관리**에서 해당 직원의 임시 비밀번호를 발급할 수 있습니다.
직원은 그 비밀번호로 로그인한 뒤 곧바로 새 비밀번호를 정하게 됩니다.

**임시 비밀번호는 발급 후 72시간(3일)이 지나면 만료됩니다.** 만료된 뒤에 그 값으로
로그인하면 "임시 비밀번호가 만료되었습니다"가 뜹니다 — 그때는 같은 방법으로 한 번 더
발급해 주세요. 만료를 두는 이유는, 발급해 두고 잊은 임시 비밀번호가 몇 달 뒤까지
그대로 통하는 상시 출입구가 되기 때문입니다(발급한 관리자는 그 값을 알고 있습니다).

당사자가 비밀번호를 실제로 바꾸면 만료는 사라집니다 — 본인이 정한 비밀번호가
3일 뒤에 막히는 일은 없습니다.

**전달할 때 함께 알려 주세요: 그 값을 그대로 다시 입력하면 안 됩니다.** 비밀번호
변경 화면에서 현재 비밀번호와 새 비밀번호를 같은 값으로 넣으면 거부됩니다. 그렇게
통과해 버리면 쪽지에 적힌 임시 비밀번호가 만료 없이 계속 통하는 상태가 되는데,
그 값은 발급한 관리자도 알고 있습니다.

**비활성화된 계정에는 발급되지 않습니다.** 발급 버튼 자체가 보이지 않고, 그래도
요청하면 "비활성화된 계정입니다"가 뜹니다. 먼저 **활성화**를 누른 뒤 발급하세요.
(예전에는 발급이 그대로 되고 당사자만 로그인에서 막혀, 관리자는 재설정해 줬다고
믿고 직원은 못 들어오는 상태가 됐습니다.)

**본인이 비밀번호를 바꾸면 다른 기기에 남아 있는 로그인은 모두 끊깁니다.** 이것이
"내 계정을 누가 쓴 것 같다"에 대한 조치입니다.

### 6-2. **관리자 본인이** 비밀번호를 잊었을 때

이 시스템에는 "비밀번호 찾기" 메일 발송이 없습니다(사내망 전용이라 메일 서버를 두지
않았습니다). 관리자가 한 명뿐인데 그 사람이 비밀번호를 잊으면, 아무도 임시 비밀번호를
발급해 줄 수 없습니다. 그때는 서버 터미널에서 아래 두 단계로 풉니다.

**1단계 — 그 계정을 지웁니다.** (직원 정보·부서·역할은 남습니다. 로그인 수단만 없어집니다.)

아래 두 줄을 통째로 복사해 붙여 넣고, `관리자이메일@gonjiam.com` 부분만 실제
이메일로 바꾸세요.

```bash
cd ~/weather
echo "delete from auth_accounts where lower(email) = lower(:'email')" \
  | docker compose exec -T postgres psql -U postgres -d weather \
      -v ON_ERROR_STOP=1 -v email='관리자이메일@gonjiam.com' -f -
```

`DELETE 1`이 나오면 지워진 것입니다. `DELETE 0`이면 이메일 철자를 확인하세요.

**2단계 — 웹 화면에서 같은 이메일로 다시 가입합니다.**
가입은 같은 이메일의 기존 직원 행에 새 계정을 이어 붙이므로, **역할(admin)은 그대로
유지됩니다.** 다시 로그인하면 관리자 메뉴가 그대로 보입니다.

> 혹시 역할까지 초기화된 것 같으면 `./ops/make-admin.sh 관리자이메일@gonjiam.com`을
> 한 번 더 실행하면 됩니다.
>
> 서버는 요청마다 역할을 다시 읽으므로 **다시 로그인하지 않아도 곧바로 관리자로
> 동작합니다.** 로그아웃·재로그인을 권하는 것은 브라우저에 남은 화면을 새로 그리기
> 위해서입니다. 다시 로그인했는데도 메뉴가 안 보이면 브라우저 강력 새로고침
> (Ctrl+Shift+R, macOS는 Cmd+Shift+R)을 해 보세요.

**이런 일을 겪지 않는 가장 좋은 방법은 관리자를 처음부터 두 명 두는 것입니다.**
설치가 끝나면 곧바로 두 번째 관리자를 지정하세요.

### 6-3. 계정이 잠겼을 때

비밀번호를 5번 틀리면 15분 동안 잠깁니다. **15분 기다리면 저절로 풀립니다.**
잠긴 사람의 화면에는 "비밀번호를 5회 잘못 입력해 계정이 잠겼습니다.
약 N분 뒤에 다시 시도하거나 관리자에게 문의해 주세요"가 뜹니다 — 로그인 실패
문구와 다르므로, 그 사람이 읽어 주는 문장만으로 잠금인지 아닌지 알 수 있습니다.

**잠겨 있어도 올바른 비밀번호를 넣으면 곧바로 로그인되고 잠금이 풀립니다.**
잠금은 *찍어 맞히기*를 막는 장치이지 비밀번호를 아는 본인을 막는 장치가 아닙니다.
이렇게 하지 않으면 **남의 이메일만 알아도 그 사람을 무기한 로그인 불가 상태로 둘 수
있습니다** — 그 대상이 특보 승인권자면 폭설이 와도 승인할 사람이 없어집니다.
그래서 비밀번호가 기억나면 15분을 기다릴 필요가 없습니다. 기억나지 않을 때만
아래 방법을 씁니다.

**"로그인 시도가 너무 많습니다. N초 뒤에 다시 시도하거나 관리자에게 문의해 주세요"**
가 뜬다면 그 이메일(또는 그 PC)에서 짧은 시간에 실패가 너무 많이 쌓인 것입니다.
사람이 오타를 몇 번 내는 정도로는 뜨지 않습니다 — 안내된 초만큼 기다리면 풀립니다.
이 문구가 자주 보인다면 자동화된 시도를 의심하고 앱 로그를 확인하세요.

**웹 화면에서 푸는 법(권장):** 직원 관리에서 그 사람의 계정 칸이 "잠김"으로 보입니다.
**비활성화**를 눌렀다가 곧바로 **활성화**를 누르면 잠금이 함께 풀립니다.
(임시 비밀번호 발급도 잠금을 풀지만, 그러면 비밀번호까지 바뀝니다 — 당사자가
비밀번호를 알고 있다면 위쪽이 낫습니다.)

**"잠금 누적 N회"가 계속 늘어난다면** 그 사람이 비밀번호를 잊은 것이 아니라 누군가
그 계정을 겨냥하고 있을 수 있습니다. 특히 특보 승인권자라면 승인이 계속 막힙니다 —
그때는 담당자에게 알리고, 앱 로그에서 `[auth] 계정 잠금:` 줄로 언제·몇 번인지
확인하세요(`docker compose logs app | grep "계정 잠금"`).

서버 터미널에서 바로 풀어야 하면:

```bash
cd ~/weather
echo "update auth_accounts set failed_attempts = 0, locked_until = null where lower(email) = lower(:'email')" \
  | docker compose exec -T postgres psql -U postgres -d weather \
      -v ON_ERROR_STOP=1 -v email='해당이메일@gonjiam.com' -f -
```

`UPDATE 1`이 나오면 풀린 것입니다.

### 6-4. 직원이 퇴사했을 때

직원 관리에서 그 사람 행의 **삭제**를 누릅니다. 확인창이 실제로 무슨 일이 일어나는지
줄줄이 알려 주는데, 요약하면 이렇습니다.

| 사라지는 것 | 남는 것 |
|---|---|
| 명부의 직원 행 | 그 사람이 승인한 특보 이력 (**승인자 이름 포함**) |
| **로그인 계정과 남아 있는 모든 세션** | 그 사람이 고친 행동 지침 (수정자 이름 포함) |
| 부서 지침 수신자 지정 · 특보 승인 수신자 지정 | 이미 나간 발송 이력 |

**삭제는 되돌릴 수 없습니다.** 잠깐 막아 두려는 것뿐이라면 삭제 대신 계정
**비활성화**를 쓰세요 — 로그인만 막히고 명부에는 남습니다.

주의할 것 두 가지:

- **그 사람이 특보 승인권자였다면 승인할 수 있는 사람이 한 명 줄어듭니다.**
  확인창이 그 사실을 알려 줍니다. 승인권자가 0명이 되면 특보가 떠도 아무도 승인할 수
  없으므로, 지우기 전에 **특보 기준** 화면의 `특보 Alert 수신자`에 다른 사람을 넣어
  두세요(§1-6의 5번). 역할을 올리는 것으로는 승인 권한이 생기지 않습니다.
- **본인은 자기 자신을 지울 수 없습니다.** 관리자가 한 명뿐인 배포에서 그것이
  가능하면 그 순간 관리자가 0명이 되기 때문입니다. 같은 이유로 **마지막 관리자는
  자기 역할을 실무자로 낮출 수도 없습니다.**

이력에 남은 이름은 화면에 `홍길동(삭제된 직원)`처럼 보입니다 — 지워졌다는 사실까지
드러나야 나중에 이력을 되짚는 사람이 오해하지 않습니다.

## 7. 자주 겪는 문제

### 7-1. 컨테이너가 안 뜬다 (`Exited (숫자)` 또는 `Restarting`)

먼저 무슨 일이 있었는지 봅니다. **로그의 마지막 몇 줄에 거의 항상 답이 있습니다.**

```bash
cd ~/weather
docker compose logs --tail 50 app
docker compose logs --tail 50 migrate
docker compose logs --tail 50 postgres
```

자주 나오는 원인:

| 로그에 보이는 것 | 원인 | 해결 |
|---|---|---|
| `password authentication failed for user "app_user"` | `.env`의 `APP_USER_PASSWORD`를 나중에 바꿨는데 데이터베이스에는 옛 비밀번호가 남아 있음 | §7-5 |
| `variable is not set` / `POSTGRES_PASSWORD가 비어` | `.env`가 없거나 값이 비어 있음 | §1-2를 다시 합니다 |
| `port is already allocated` | 8080(또는 5433) 포트를 다른 프로그램이 이미 쓰고 있음 | 그 프로그램을 끄거나, **`.env`에** `APP_HOST_PORT=8090`(웹 화면) / `POSTGRES_HOST_PORT=5443`(데이터베이스)을 적고 `docker compose up -d`. `docker-compose.yml`을 직접 고치면 다음 `git pull`에서 충돌합니다 |
| `no space left on device` | 디스크가 참 | `docker system prune -a`로 안 쓰는 이미지를 지웁니다(데이터 볼륨은 안 지워집니다) |
| `relation "..." does not exist` | 스키마가 안 만들어짐 | `docker compose logs migrate`를 보고 §7-2 |

로그 마지막 줄이 `ExperimentalWarning: Transform Types is an experimental feature`라면
**그건 오류가 아닙니다.** §7-6을 보세요.

고쳤으면 다시 올립니다.

```bash
docker compose up -d --build
```

### 7-2. `migrate`가 실패한다 / 로그에 처음 보는 줄이 나온다

```bash
docker compose logs migrate
```

`migrate`가 실패하면 **앱은 뜨지 않습니다.** 이미 돌고 있던 앱이 있다면 그건 그대로
계속 돌고(예전 버전으로 서비스가 유지됩니다), 업데이트만 중단됩니다. 화면에는
`service "migrate" didn't complete successfully: exit 1`이 찍힙니다.

#### 정상인 줄 (그냥 넘어가세요)

| 로그 | 뜻 |
|---|---|
| `→ 0011_auth_rls.sql 적용` | 새 스키마 변경을 적용하는 중입니다 |
| `마이그레이션 10개를 적용했습니다.` | 첫 설치가 끝났습니다 |
| `스키마가 이미 최신입니다.` | 바뀐 것이 없어 아무것도 하지 않았습니다 |
| `기본 데이터(seed)는 첫 설치 때 이미 들어갔습니다 — 건너뜁니다.` | 정상입니다(§2 "기본 데이터" 참고) |
| `NOTICE: relation "schema_migrations" already exists, skipping` | 정상입니다 |
| `이미 만들어진 데이터베이스입니다 — 기존 마이그레이션을 적용 완료로 기록합니다` | 아래 "기존 데이터베이스를 옮겨 왔을 때" |

#### 오류별 조치

- `데이터베이스에 접속할 수 없습니다` → postgres가 아직 준비되지 않았습니다.
  `docker compose up -d`를 한 번 더 실행하면 대개 해결됩니다.
- `중단: 이 데이터베이스는 스키마가 있지만 최신이 아닙니다` → 아래 "기존 데이터베이스를
  옮겨 왔을 때"를 보세요.
- `type "event_kind" already exists` 같은 "이미 있다" 오류 → 스키마는 이미 만들어져 있는데
  적용 기록이 어긋난 상태입니다. 아래로 무엇이 기록돼 있는지 확인하고, 조치가
  필요하면 개발 담당자에게 이 출력을 그대로 전달하세요.

  ```bash
  docker compose exec -T postgres psql -U postgres -d weather -c "select * from schema_migrations order by filename"
  ```

`migrate`만 다시 돌려 보려면 그냥 다시 올리면 됩니다. `migrate`는 항상 앱보다 먼저 돕니다.

```bash
docker compose up -d
```

> `docker compose run --rm migrate`도 있지만, `docker-compose.yml`이 방금 바뀐 직후에는
> 이 명령이 postgres 컨테이너까지 다시 만들려다 실패할 수 있습니다. **`up -d`를 쓰세요.**

#### 기존 데이터베이스를 옮겨 왔을 때

다른 서버에서 쓰던 데이터베이스를 그대로 가져다 붙이면, 그 데이터베이스에는 "어떤
스키마 변경을 적용했는지"의 기록이 없습니다. 이때 `migrate`는 스키마를 살펴보고
**이미 다 적용된 상태라고 판단되면** 아래 줄을 찍고 기록만 새로 남깁니다.

```
이미 만들어진 데이터베이스입니다 — 기존 마이그레이션을 적용 완료로 기록합니다
```

**이 줄은 정상입니다.** 처음 옮겨 온 그 한 번만 나오고, 그 뒤로는 나오지 않습니다.

> **옮겨 온 데이터베이스에서 폭설 반복 정책을 손수 바꿔 두었다면** 한 번 확인하세요.
> `0015`가 폭설을 "오늘 누적 적설량 기준"으로 바꾸면서 **누적 임계값(`repeat_accum_threshold`)을
> 비웁니다.** 새 정책에서는 그 값을 쓰지 않으므로 동작에는 영향이 없지만, 손수 넣어 둔
> 숫자는 안내 없이 사라집니다. 알림 설정 → 반복 알림 정책에서 지금 값을 확인하세요.

옮겨 온 데이터베이스가 **옛 버전**이면 이렇게 멈춥니다.

```
중단: 이 데이터베이스는 스키마가 있지만 최신이 아닙니다.
  적용된 흔적이 없는 마이그레이션: 0004_dispatch_snapshot.sql, 0007_...
```

이때는 **아무것도 하지 말고 개발 담당자에게 이 메시지를 그대로 전달하세요.**
억지로 진행시키면 빠진 변경들이 "적용 완료"로 잘못 기록되어 앞으로 영원히
적용되지 않습니다. 화면은 멀쩡히 뜨지만 나중에 특보를 발송할 때 터집니다.
그래서 시스템이 일부러 멈추는 것입니다.

### 7-3. 수집이 멈췄다 (특보가 안 뜬다)

`/api/health/deep`이 `관측 수집이 ...멈춰 있습니다` 또는 `...모두 결측입니다`를 보일 때입니다.

**1) 앱 로그에서 수집 실패 이유를 봅니다.**

```bash
docker compose logs --tail 100 app | grep -i "weather-tick\|kma\|실패"
```

**2) 원인별 조치**

| 로그에 보이는 것 | 원인 | 해결 |
|---|---|---|
| `SERVICE_KEY_IS_NOT_REGISTERED` / `인증키` 관련 | 기상청 인증키가 잘못됐거나 만료됨 | 공공데이터포털에서 키를 다시 확인해 `.env`의 `KMA_API_KEY`를 고치고 `docker compose up -d` |
| `LIMITED_NUMBER_OF_SERVICE_REQUESTS` | 기상청 일일 호출 한도 초과 | 다음 날 자동으로 풀립니다. 반복되면 포털에서 한도 상향을 신청하세요 |
| 응답은 오는데 값이 비어 있음 | 격자좌표(nx, ny)가 잘못됨 | **알림 설정 → 관측 지점**에서 좌표를 다시 확인(nx 1~149, ny 1~253). `/api/health/deep`이 좌표를 사유로 실어 줍니다 |
| 아무 로그도 없음 | 앱이 죽어 있거나 스케줄러가 안 돎 | `docker compose restart app` 후 5분 뒤 다시 확인 |

**3) 앱을 다시 띄우면 놓친 수집을 한 번 따라잡습니다.**

```bash
docker compose restart app
# 2분 기다렸다가
curl -s localhost:8080/api/health/deep
```

### 7-4. 화면은 열리는데 아무것도 안 된다 / `unhealthy`로 표시된다

**주의:** 데이터베이스가 죽었을 때 `docker compose ps`는 `unhealthy`가 아니라 그냥
`Up (healthy)`로 보입니다(§3-1의 "중요 1"). 즉 **`ps`만 보고 안심하면 안 됩니다.**
로그인이 안 되거나 목록이 비어 보이면 아래를 순서대로 하세요.
`unhealthy`가 실제로 떴을 때도 같은 절차입니다 — Docker는 그걸 보고도 아무것도
해 주지 않으므로 사람이 조치해야 합니다.

```bash
cd ~/weather
# 1) 무엇이 문제인지 물어봅니다
curl -s localhost:8080/api/health/deep

# 2) 응답이 아예 없으면 앱 로그를 봅니다
docker compose logs --tail 50 app

# 3) 데이터베이스가 살아 있는지 봅니다
docker compose exec -T postgres pg_isready -U postgres -d weather
```

- `데이터베이스에 연결할 수 없습니다`가 보이면 → postgres부터 살립니다.

  ```bash
  docker compose restart postgres
  # 30초 기다렸다가
  docker compose restart app
  ```

- `pg_isready`가 실패하면 → `docker compose logs --tail 50 postgres`를 보고 §7-1의 표를 확인합니다.
- 그래도 안 되면 전체를 다시 올립니다. **`-v`는 절대 붙이지 마세요.**

  ```bash
  docker compose down
  docker compose up -d
  ```

### 7-5. 비밀번호를 바꿨더니 앱이 데이터베이스에 못 붙는다

`.env`의 `APP_USER_PASSWORD` / `APP_SERVICE_PASSWORD`를 고쳐도, 데이터베이스 안에 이미
만들어진 계정의 비밀번호는 자동으로 바뀌지 않습니다. 아래로 맞춰 줍니다.

```bash
cd ~/weather
# .env의 값을 그대로 읽어 데이터베이스 쪽 비밀번호를 맞춥니다
set -a; . ./.env; set +a
echo "alter role app_user password :'pw'" \
  | docker compose exec -T postgres psql -U postgres -d weather \
      -v ON_ERROR_STOP=1 -v pw="$APP_USER_PASSWORD" -f -
echo "alter role app_service password :'pw'" \
  | docker compose exec -T postgres psql -U postgres -d weather \
      -v ON_ERROR_STOP=1 -v pw="$APP_SERVICE_PASSWORD" -f -
docker compose restart app
```

> 왜 `-c "..."`가 아니라 `echo ... | ... -f -` 인가: `psql -c`로 준 문장은 `:'pw'` 같은
> 변수 치환을 거치지 않고 그대로 데이터베이스로 가서 `syntax error at or near ":"`가
> 납니다(실제로 겪었습니다). 표준입력으로 흘려 `-f -`로 읽혀야 값이 제대로 꽂힙니다.

> `POSTGRES_PASSWORD`는 **볼륨을 처음 만들 때 한 번만** 반영됩니다. 나중에 `.env`에서
> 바꿔도 데이터베이스 쪽은 안 바뀝니다. 슈퍼유저 비밀번호까지 바꿔야 한다면
> 개발 담당자에게 문의하세요.

### 7-6. 로그에 `ExperimentalWarning`이 뜬다 — 정상입니다

앱을 띄울 때마다 로그 맨 앞에 이런 줄이 나옵니다.

```
(node:1) ExperimentalWarning: Transform Types is an experimental feature and might change at any time
```

**고장이 아닙니다. 무시하세요.** 이 시스템은 TypeScript 소스를 따로 빌드하지 않고 Node가
실행 시점에 타입을 벗겨 내는 방식(`--experimental-transform-types`)으로 돕니다. 배포되는
코드가 저장소의 코드와 글자 그대로 같아지는 장점이 있고, 대신 Node가 "이 기능은 아직
실험 단계"라고 매번 알려 줍니다. 장애 조사 중에 이 줄이 보이면 그냥 넘기고 그 아래
줄을 보세요.

### 7-7. 로그인이 안 된다

| 증상 | 원인 | 해결 |
|---|---|---|
| "회사 이메일로만 가입할 수 있습니다" | `.env`의 `ALLOWED_EMAIL_DOMAINS`에 없는 도메인 | 값을 확인하고 필요하면 콤마로 추가한 뒤 `docker compose up -d` |
| "로그인할 수 없습니다" | 이메일 또는 비밀번호가 틀림 | 철자 확인. 계속 틀리면 §6-1 |
| "비밀번호를 5회 잘못 입력해 계정이 잠겼습니다 · 약 N분 뒤에..." | 5회 실패로 15분 잠김 | **비밀번호가 기억나면 그대로 넣으면 됩니다**(잠금이 함께 풀립니다). 기억나지 않으면 §6-3 |
| "로그인 시도가 너무 많습니다 · N초 뒤에..." | 짧은 시간에 실패가 너무 많이 쌓임(속도 제한) | 안내된 초만큼 기다리세요. 본인이 그만큼 시도하지 않았다면 §6-3의 "잠금 누적" 문단 |
| 로그인 버튼을 눌러도 다시 로그인 화면으로 돌아옴 | `http`로 접속하는데 `.env`의 `COOKIE_SECURE=true`라 세션 쿠키가 안 내려감 | `.env`에서 `COOKIE_SECURE=false`로 고치고 `docker compose up -d` |
| 화면이 아예 안 열림 | 앱이 안 떴거나 포트 문제 | §7-1, §7-4 |
| 관리자 메뉴가 안 보임 | 역할이 아직 실무자 | §1-5 |

## 8. 환경변수 (`.env`)

`.env`는 §1-2에서 만든 파일입니다. 값을 고친 뒤에는 반드시 아래를 실행해야 반영됩니다.

```bash
docker compose up -d
```

| 이름 | 무엇인가 | 나중에 바꿔도 되나 |
|---|---|---|
| `POSTGRES_PASSWORD` | 데이터베이스 최고 관리자 비밀번호. 백업·복구·관리 명령에 쓰입니다. | ❌ 볼륨을 처음 만들 때만 반영됩니다 |
| `APP_USER_PASSWORD` | 앱이 **권한 정책을 적용받으며** 접속할 때 쓰는 비밀번호 | ⚠️ 바꾸면 §7-5도 함께 해야 합니다 |
| `APP_SERVICE_PASSWORD` | 앱이 **수집·발송처럼 사용자를 대신하지 않는 일**을 할 때 쓰는 비밀번호 | ⚠️ 위와 같음 |
| `DATABASE_URL` | 호스트에서 데이터베이스에 직접 붙을 때 쓰는 주소. 컨테이너로 운영할 때는 쓰이지 않습니다. | ✅ |
| `ALLOWED_EMAIL_DOMAINS` | 가입을 허용할 이메일 도메인. 콤마로 여러 개(`gonjiam.com,example.com`) | ✅ |
| `APP_BASE_URL` | 카카오워크 DM에 넣는 링크의 기준 주소. **사내에서 실제로 접속하는 주소**를 적습니다. 틀리면 DM의 링크를 눌러도 안 열립니다. | ✅ |
| `KMA_API_KEY` | 기상청 공공데이터포털 단기예보 조회서비스 **일반 인증키(Decoding)**. 없거나 틀리면 수집이 통째로 멈춥니다. | ✅ |
| `KAKAOWORK_BOT_KEY` | 카카오워크 봇 앱키. **비워 두면 발송이 실제로 나가지 않고 로그에만 찍힙니다**(설치 직후 점검용). | ✅ |
| `NOTIFY_CHANNEL` | `console`로 두면 카카오워크 대신 **앱 로그로만** 발송합니다(시연·설치 점검용). **운영에서는 반드시 비워 둡니다** — 남아 있으면 모든 화면이 초록이고 승인이 "발송 1명"으로 성공하는데 **아무도 받지 못합니다**(§1-6의 7번). 연결된 수신자가 한 명이라도 있는데 이 값이 `console`이면 `/api/health/deep`이 503으로 그 사실을 말합니다 | ✅ |
| `COOKIE_SECURE` | `https`로 서비스할 때만 `true`. `http`인데 `true`면 로그인이 되지 않습니다(§7-7). | ✅ |
| `APP_HOST_PORT` | 웹 화면 포트(기본 8080). 8080을 다른 프로그램이 쓰고 있을 때만 적습니다 — 적으면 접속 주소도 그 포트로 바뀝니다 | ✅ |
| `POSTGRES_HOST_PORT` | 서버에서 데이터베이스에 직접 붙을 때 쓰는 포트(기본 5433). 겹칠 때만 적습니다 | ✅ |

## 9. 용어

| 말 | 뜻 |
|---|---|
| 컨테이너 | 프로그램 하나를 통째로 담아 둔 상자. 서버에 프로그램을 직접 설치하지 않아도 됩니다. |
| 볼륨 | 컨테이너를 지워도 남는 저장 공간. 데이터베이스 내용이 여기 들어 있습니다. |
| 마이그레이션 | 데이터베이스의 표 구조를 만들거나 바꾸는 작업. `migrate` 컨테이너가 합니다. |
| 스키마 | 데이터베이스의 표 구조 |
| 시드(seed) | 처음에 넣어 두는 기본값(부서 트리, 특보 기준 등) |
| 하트비트 | "언제 마지막으로 수집했는가"를 기록해 두는 값. §3-3이 이걸 봅니다. |
| 결측 | 수집은 시도했는데 값을 못 받아 비어 있는 상태 |
| 로그 | 프로그램이 남기는 기록. 무엇이 잘못됐는지는 거의 항상 여기에 있습니다. |
